Agent Memory Is a Team Document, Not a Personal Recall

Two arguments that end in the same place: write knowledge down where the whole team can read it, and treat everything else as hidden state.

2,100 words~9 min read2026-10-05

Two posts, one conclusion

Earlier this year I wrote a short note about memory for agents that many people share: a team Slack bot, a shared coding assistant, a skill catalog. My argument was about scaling. Team memory compounds as more people use it. Personal memory does not. So build the team layer first.

Then I read “Agents Don’t Need Memory. They Need Documentation.” on liao.gg. It comes at the problem from the opposite end, a single developer with a single agent, and argues that the whole memory plugin category solves the wrong problem. Retrieval over old conversations is not understanding. Documents are.

One post starts from the team and the other from the individual, and both arrive at the same design: agent knowledge should live in plain documents that humans can read, review, and share. Anything outside those documents is hidden state, and hidden state hurts. This post puts the two arguments together.

What “memory” means today

The liao.gg post describes the standard memory plugin in five steps:

  1. Go through session transcripts.
  2. Generate snippets of “memories”.
  3. Insert them into a vector database.
  4. On every prompt, retrieve the top five and inject them.
  5. If that is not enough, give the agent a tool to search the database.

Fancier tools add tiers (short-term and long-term), background jobs that merge and deduplicate, overnight “dreamers” that rewrite memories, rerankers. Each one adds tokens on top of the same base. The post names five problems with that base:

ProblemWhat goes wrong
Recall by similarityEmbedding distance tells you two snippets look alike. It does not tell you which one is correct, which one is current, or what is missing.
No contextA snippet loses the motivation, the trade-offs, and the environment it came from.
The past is treated as truthThe code changes every day. How many of the 500 snippets about authentication are still accurate?
Unknown unknownsA search tool only helps if the agent knows it should search. It does not know what it does not know.
Cannot be auditedTen thousand embeddings in SQLite. Which are stale? Which are wrong and quietly steering the agent?

The fix it proposes is simple. Give the agent a structured folder of Markdown documents (instructions, specs, decisions, research, indexes). The loop changes from prompt → build → forget to prompt → consult → build → update. The agent reads the relevant documents before it works and updates them after, while the full picture is still in context. The author has run this for over a year and released it as Operator Memory.

That is an argument about quality. My earlier note was an argument about scale. Before putting them together, it helps to see that “memory” is not one thing.

Three kinds of memory, three lifecycles

Cognitive science splits long-term memory into kinds. The split is useful for agents because each kind needs a different lifecycle. The basic mistake of memory plugins is one store and one lifecycle for all three.

KindAgent formExampleLifecycle
EpisodicChats, session transcripts“On Tuesday we tried a retry loop and it failed.”Recall when relevant, then forget.
ProceduralSkills, runbooks, SOPs“How to deploy the auth service.”Evolve with the system it acts on.
SemanticKnowledge“Auth tokens rotate every 15 minutes.” “A settled order cannot be edited.”Stable. Organized by domain.

Episodic memory: recall, then forget

A chat records what happened, not what is true. It answers “what was I doing yesterday?” and it should fade. Memory plugins keep every episode forever and serve snippets of it back as if they were facts. That is where the liao.gg problem “the past is treated as truth” comes from. For episodic memory, forgetting is a feature. Keep it personal, keep it short-lived, and never let it be the authority on how the system works.

Procedural memory: evolve with the system

A skill encodes how to do something against a specific system: which command to run, which check to pass, which order to follow. When the system changes, the skill must change too, or it breaks. So skills belong in version control next to the code they drive. They have owners, they have tests or evals, and they change in the same review as the system change. A procedure stored as a memory snippet cannot be updated when the deploy command changes, because nobody knows it exists.

Semantic memory: stable and domain-driven

Knowledge is facts and concepts: what the order service owns, what “settled” means, why the team chose event sourcing. It should be stable. It changes when someone makes a decision, not when a background job rewrites it overnight. And it should be organized by domain, in the sense of domain-driven design: one place per bounded context, written in the team’s shared language. It should not be organized by when you learned it or which session it came from.

A domain structure also answers the “unknown unknowns” problem. An agent working in billing does not need similarity search to find the right context. It reads the billing document, because the structure tells it where to look.

This maps directly onto both posts. The liao.gg brain holds instructions (procedural) and specs, decisions, and research (semantic). It leaves out transcripts (episodic) on purpose. And on the team-versus-personal axis, episodic memory is personal and short-lived, while procedural and semantic memory are team assets.

Team memory scales. Personal memory does not.

Team memory is a knowledge base. You write a runbook once and every engineer on the team benefits. More contributors make it richer. It is the same reason we write wikis and READMEs: pay the cost of learning once and share it.

Personal memory is a social layer. It makes the agent feel like it knows you: your preferences, your history, what you were working on last Tuesday. That has real value for engagement. But N users means N separate memory islands. Alice’s conversation history cannot help Bob.

PriorityLayerScales?Private?Purpose
1stTeam memoryYesNoShared knowledge: runbooks, architecture, conventions, decisions
2ndPersonal memoryNoYesIndividual preferences, private context, style

Put the two posts side by side and the link is clear. A vector store of conversation snippets is personal memory by construction: it is built from one person’s sessions, on one machine, and nobody else can read it. A folder of Markdown documents is team memory by construction: you can commit it, review it in a pull request, and give it to the next engineer. Choosing documents over recall is also choosing the layer that scales.

Most personal memory is a view of team memory

Much of what gets stored as personal memory is not personal knowledge. It is team knowledge seen through a personal preference.

Say the team has an architecture document. Alice wants the key decisions and no detail. Bob wants the full trade-offs. The knowledge is the same. Only the rendering style differs, and that is a preference, not knowledge. So you do not copy the architecture document into each person’s memory. You store style: high_level for Alice and style: detailed for Bob, and apply it when the team document goes into context.

This makes the personal layer much smaller than it first looks:

  • Store personally: style preferences, private project context, things that are actually about you.
  • Do not store personally: anything that is true about the system. That belongs in a team document.

A memory plugin that extracts “the auth service uses token rotation every 15 minutes” from your chat and files it in your private vector store has put team knowledge in the wrong place. It is now invisible to everyone else and will go stale without anyone noticing.

“Update” is the promotion step

In my earlier note I asked how knowledge should move from personal to team. Alice learns that you should always run integration tests before you deploy the auth service. It starts as her personal lesson. If it is a team-wide practice, it belongs in the runbook, not locked in Alice’s memory where Bob can never find it. I called this a promotion workflow.

The update step in prompt → consult → build → update is that same workflow, done at the right moment. At the end of a task the agent has the full context: what it tried, what failed, what the user corrected. That is the cheapest time to write the lesson down, and the place to write it is the shared document, not a private store.

In terms of the three kinds, promotion turns an episode into something durable. Alice’s lesson becomes a step in the deploy skill (procedural). A fact she discovered about token rotation goes into the auth domain document (semantic). After that, the chat it came from can be forgotten.

For a team there is one more rule. Shared documents need a review gate:

  • Agents propose and humans approve changes to team documents. A diff in a pull request is easy to review. An embedding is not.
  • No personal data in team memory. Names, performance notes, and personal details stay in the personal layer.
  • Personal memory can be written automatically. It is private, small, and limited to preferences, so the risk is low.

A plain-file brain makes all three rules cheap, because the tools already exist: git, code review, ownership files. A vector database would need you to build them from nothing.

Personal memory is hidden state

The liao.gg post calls the memory store unauditable. In a team the cost is worse than that. When memory is not portable, it becomes hidden state, and hidden state silently changes how the agent behaves. You cannot fix what you cannot reproduce, and you cannot reproduce what lives only on one person’s machine.

Two cases where this hurts:

  1. Stale memory. Your local agent remembers that your SSO token was expired. That was true on Monday. On Thursday it still plans around it. A wrong memory leads to wrong behavior, and nobody can see why.
  2. Environment anchors. You keep a local folder of notes for on-call ticket work, and the agent learned to look there. On a teammate’s laptop the path does not exist. Same agent definition, same prompt, different environment, different result.

In both cases your agent plus your hidden memories will not behave the same way for your teammate, even with an identical skill or agent definition. For that reason, in the agent tooling I work on, we prefer no-memory mode. We would rather lose some personalization than lose the ability to reproduce a teammate’s failure, add a guardrail as the fix, and confirm it works. Agents are still non-deterministic, but this removes a large class of “works on my laptop” bugs.

Document-based memory changes this trade-off. If the agent’s knowledge is a set of files in the repository, it is no longer hidden. It is versioned input like any other. A teammate who checks out the same commit gets the same brain. A failure can be reproduced, and the fix can be a one-line edit to a document instead of a support thread. Documents give you much of the value of memory without the cost to reproducibility.

Putting it together

Here is the combined design for a multi-user agent:

  1. Sort memory by kind before you store it. Episodic, procedural, and semantic memory each get their own place and their own lifecycle.
  2. Let episodes expire. Chats are personal, can be searched for a while, and are then forgotten. They are never served as facts.
  3. Version skills with the system. Skills live next to the code, have owners and evals, and change in the same review as the system they act on.
  4. Keep knowledge stable and organized by domain. One document per bounded context, in the team’s shared language, as plain Markdown in version control.
  5. Consult before work, update after. The agent reads the relevant skill and domain documents first. When it finishes, it promotes what it learned into a skill or a domain document while the context is fresh.
  6. Load team knowledge before personal memory in every prompt. The team document is the authority. Personal memory only adds to it.
  7. Keep personal memory to preferences. Style, verbosity, private context. Never facts about the system.
  8. Send updates through review. Agents propose changes to team documents. Humans approve them. No personal data goes in.
  9. Treat anything that does not live in a document as hidden state. Default to no memory when you need to reproduce, evaluate, or debug.

Neither post is against personalization. Both say that personalization is the small part of the problem. The large part is the agent understanding the project, and that is a documentation problem that the whole team shares.

An agent that knows the team is more useful than an agent that knows you, because it scales. An agent that reads documents is more useful than one that recalls snippets, because you can check what it knows.
