From Merge Queues to Merge Plans: What OpenAI’s and Anthropic’s Git Rewrites Leave Unsolved

Agents pushed both labs past what their source control could handle, and both rebuilt it within months. They fixed the bytes: pushes, fetches, and checkouts. Neither fixed the race of many writers on one trunk. Agents can fix that in a way people never could, by planning the writes instead of racing them.

2,700 words~12 min read2026-11-19

In short

  • Within three weeks of each other, Anthropic and OpenAI described how they rebuilt source control for agents. Anthropic’s merges went from about 2,500 a day to more than 30,000 in four months, and it replaced git with Scion. OpenAI’s trunk commits reached 14.8 times their Q1 2024 rate, and it built Pando, a new server behind the Git protocol.
  • Both fixed the bytes: pushes, fetches, and checkouts. Neither fixed coordination: many writers, one trunk. Pando still orders pushes to the same branch, and Anthropic gave up the merge-queue lock and lets Claude repair conflicts after they land.
  • Velocity and documentation as code will keep pushing the load up. New servers, source control as an API, and cheap repair absorb much of it, but none of them removes the race for the trunk.
  • The disruptive move is a planner that sees every write request before any code exists, predicts what each will touch, and schedules parallel waves and stacked chains. Conflicts are avoided instead of discovered at push time.

Two labs hit the same wall

On 13 October, Anthropic published Redesigning source control at Anthropic. It merged about 2,500 code changes a day in May 2026, and more than 30,000 a day in September. The history of its main branch is almost 100 GB, and CI alone runs on the order of 25 million checkouts a day. A team of seven built a new version control system, Scion, and moved the monorepo off git in five months.

On 2 November, OpenAI published Scaling Git at OpenAI. Its monorepo landed 14.8 times as many commits on the main branch in Q3 2026 as in Q1 2024, and OpenAI expects about 25 times in Q4. From around the end of 2025, its systems struggled: slow fetches and pushes, failed merges, and reliability at times below 90%. In ten weeks, OpenAI built Pando, a new backend that keeps the Git protocol and client.

Both name the same cause. Anthropic: “coding is no longer the bottleneck … The bottleneck, now, is all of the developer infrastructure built for human scale: source control, builds, and CI.” OpenAI: “One engineer now has several changes ready for CI at once, and each push can set several jobs fetching the same commit.”

The labs are first, not alone. GitHub’s Octoverse 2026 counts 3.5 million merged pull requests a day, more than three times the rate of two years ago, and more than 40% of pull requests now start with an agent. Anthropic expects this class of problems to become more common over the next six to twelve months. Small teams already feel a small version of it: a few people and their agents in one codebase get a steady stream of merge conflicts and slow rebases.

What they fixed: the bytes

The two take opposite routes. OpenAI kept Git’s protocol and client and replaced the server. Anthropic replaced git, and moved most of the work to the server.

OpenAI: PandoAnthropic: Scion
ApproachA new server behind the unchanged Git protocol and clientA new system. The server commits, merges, rebases, and answers history and blame. The client is thin.
WritesEach branch is coordinated on its own, so pushes to different branches never wait on each otherChangesets in a write-ahead log, created on the server, with no packfiles and no locks
ReadsReuses stored packfiles across clients, from regional caches with hit rates over 99%Fetches only the trees and blobs a client needs, with sparse and virtual checkouts
ResultMedian push latency down about 80%, and nearly a petabyte served a dayInfrastructure 200 times smaller than the old git mirrors, and checkouts in seconds instead of minutes
Built inTen weeks: one engineer’s design, implemented by teams of agentsFive months: a team of seven, working with Claude

Neither solved coordination. Pando is explicit: “Clients only conflict when pushing to the same ref simultaneously.” That beats designs that put every push in one global order, but in trunk-based development, every change ends on the same ref. Anthropic says it directly:

“A proper merge queue, for example, doesn’t make much sense at agent scale. What does CI even mean when hundreds or even thousands of changes can merge while tests are running? We haven’t been able to effectively replicate the industry standard of a global repository lock on the merge queue, so instead, we’ve invested in post-merge and pre-deploy automated testing. This does mean that concurrent changes can conflict, but Claude can typically fix these conflicts faster than humans can even identify them.”

What they left open: many writers, one trunk

Some arithmetic shows why the lock breaks. Say the tests take 20 minutes. A queue that lands one change at a time lands 72 a day. To land 30,000 a day, each test run must carry about 420 changes. If 1% of changes would fail on their own, a batch of 420 passes with a probability of 0.99420, about 1.5%. Nearly every batch fails, and must be split to find the culprit. Batching, speculative builds, and culprit finding stretch the queue, and Uber’s SubmitQueue keeps a monorepo’s main branch green at thousands of commits a day. But they still treat the trunk as one resource that every change must win.

There are four ways to share one resource among many writers, and databases have a name for each:

StrategyHow writers share the trunkDatabase analogueCost at agent scale
SerializeA merge queue with one global lock lands one change, or one batch, at a time, after its tests passSerial execution under a global lockThroughput is capped by test time, and large batches almost always fail
DetectEveryone pushes. A compare-and-swap on the branch rejects the late writer, who rebases and retries. Pando makes this fast across branches.Optimistic concurrency controlRetries grow with contention, and every change contends for the trunk and its hot files
RepairMerge without a lock, test after merge and before deploy, and let an agent fix what breaks. Anthropic’s choice.Eventual consistency with compensating fixesThe trunk is sometimes broken, so detection and fixes must be fast

People live with serialize and detect, because a person’s intent is private until they push. Repair became practical once an agent could fix a conflict in a minute. Plan becomes practical only when the writers are agents. I come back to it after the trend factors.

What keeps pushing the load up

Velocity. Agents raise both the number of changes and the number in flight at once. OpenAI’s trunk commits grew about four times in the three quarters to Q3 2026, and Anthropic’s merges grew twelve times in four months. Anthropic expects no slowdown: “the latent demand for merging code is practically infinite, and every bottleneck we remove immediately leads to a further increase in the amount of code we produce.” Smaller changes, which every agent workflow encourages, make review easier and merges more frequent.

Documentation as code. I have argued for more of it on this blog: agent memory as a team document in the repo, and data contracts, skills, agent specs, and review rules as code. Each of those adds Git load, in three ways:

  • Wider changes. A change updates the code, the spec, and the docs together. On GitHub, 87% of agent-started pull requests change more than one file, against 79% of the rest.
  • Hot files. A root AGENTS.md, a shared spec index, a changelog, a lockfile: files that unrelated changes all touch. A hot file turns independent work into conflicting work.
  • More readers. Every agent session reads the context files before it writes anything. GitHub found that new repositories with an agent configuration file logged eight times as many commits as new repositories without one. That is a correlation, not a cause, but it points the same way.

Readers multiply faster than writers. Each change starts CI jobs, agent sandboxes, and eval runs, and each wants a checkout. Anthropic’s 25 million checkouts a day come to roughly 800 for every merged change. Fetched naively, Anthropic estimates, that would be more than 600 PB of git traffic a day.

What absorbs it

  • New servers behind the same client. Pando shows that the Git protocol is not the limit: coordinate each branch on its own, serve the same packs to many readers, and cache near the clients. OpenAI sends its Git client fixes upstream, and Anthropic suggests server-side APIs that forges could standardize.
  • Source control as an API. When the server answers diff, blame, merge-base, and history, most jobs need no clone at all. The rest check out sparsely and pay only for what they read.
  • Fewer branches. Scion discourages refs other than the main and release branches. Agent work becomes short-lived changes on the server, not branches that live for weeks.
  • Cheap repair. A conflict that an agent resolves in a minute is not the problem it was for a person who lost an afternoon to a rebase. Anthropic runs its monorepo on this.
  • Hot files designed away. The AGENTS.md guidance already recommends a nested file per package in a large monorepo, so no single file is edited by every change. The same works elsewhere: a changelog fragment per change, and indexes generated on merge instead of edited by hand. A generated file has one writer, the build.

Weighing the two sides, here is what I expect over the next 12 to 24 months:

The disruptive option: plan the writes

Today, writers work in parallel and find each other at push time. For people, that is the only practical choice. A person’s intent stays in their head until they push, and people pick their own tasks.

Agents change both facts. An agent’s intent is written down before it writes any code: the task, the spec, the plan. And agents take assignments. So one orchestrator, a merge planner, can see every pending write request for a repository, and decide who writes what, in which order.

A merge planner does four things:

  • Predict each footprint. For each intent, predict the files, symbols, and build targets it will touch, from the spec, the code index, and similar past changes. Ask the agent for a short plan before it codes, and treat the plan as a declaration. Precise specs make the prediction better, one more reason to give specs structure.
  • Find the overlaps. Two intents overlap if their footprints share a file. To catch conflicts that a text merge misses, they also overlap if they share build targets downstream.
  • Schedule waves and stacks. Run the intents that do not overlap in parallel. Stack an overlapping intent on its predecessor, so it starts from the predecessor’s result and merges after it. The merge chain is decided up front, not discovered at push time. Fold near-duplicates into one change, give each hot file one writer, and give a waiting agent other work.
  • Hold each change to its declaration. A diff that touches a file outside its footprint goes back to the planner. Detect and repair stay behind the planner as the safety net.

Databases already work this way. Calvin (SIGMOD 2012) agrees on the order of transactions before it executes any of them, so conflicting transactions run in the agreed order instead of aborting and retrying. Each transaction must declare its read and write sets in advance. When one cannot, Calvin first runs a cheap, read-only reconnaissance query to discover them, and checks at execution time that they still hold. For an agent, the planning pass is the reconnaissance, and the footprint check is the validation.

Researchers proposed the same for people. Crystal (FSE 2011) merged developers’ work in the background to warn them of conflicts early, and Cassandra (ICSE 2013) scheduled developers’ tasks to minimize conflicts. Neither changed how teams work, because people choose their own tasks and do not publish their intent before they code. Agents do both by default.

The pieces exist: merge queues, agents that plan before they code, and stacked pull requests, which GitHub launched in preview on 30 July 2026 and more than 264,000 developers had used by September. What is missing is the piece that decides the stacks before anyone writes the code.

Where planning breaks

  • Wrong predictions. A footprint is a guess. Measure how often diffs stay inside their footprints, and keep detect and repair behind the planner for the times they do not.
  • The planner as a new global lock. One planner for a whole monorepo would become the bottleneck the merge queue was. Partition planners by ownership boundary, the same move Pando made when it coordinated each branch on its own.
  • Waiting in a stack. A stacked change waits for its predecessor. Urgent fixes need a fast lane.
  • Conflicts no footprint shows. Two changes can touch different files and still break each other. Build-graph footprints catch more of them, and testing after merge catches the rest.

The planner earns its place if conflicts per merged change fall faster than the time spent waiting in stacks grows.

Git was designed for people who work offline and reconcile later, so its concurrency is optimistic: everyone writes, and conflicts surface at merge. OpenAI and Anthropic have shown that the storage side of source control can scale to agents, by rebuilding the server. Coordination is next. Agents are always online, their intents are written down, and they accept a schedule. The next source control system will be a faster server, and also a scheduler that decides who writes what, and in which order, before the code exists.
