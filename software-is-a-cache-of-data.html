The Cache Inversion: Software Is Becoming a Cache of Data

We used to store data to cache the results of software. More and more often, the software is now the cache: a distilled form of data too large to keep in hand. Code that models how a system behaves is still essential, but this trend changes how we build, version, and test software.

1,600 words~7 min read2026-11-12

Software 1.0, 2.0, and 3.0, all at once

Andrej Karpathy gave us useful names. Software 1.0 is code that humans write. Software 2.0 is the weights of a neural network, learned from data instead of written by hand. Software 3.0 is a large language model steered by prompts, context, and instructions in natural language.

These are not eras that replace one another. Our organization runs all three at the same time, often in the same request path. A service written in Java calls a model retrained every quarter, and an agent driven by a prompt reviews the code of both.

FormWhat defines behaviorWhere the behavior comes fromHow it changes

Software 3.0Prompts, context, and the base modelPretraining data, plus the context we give at run timeChange the context, or swap the model

If you read down the third column, you see a trend. The further right we move on this spectrum, the less the behavior lives in something a human wrote, and the more it lives in data. So the old definition, “software is the codebase,” no longer covers what we ship.

This is not abstract for us. Our organization has invested deeply in automation and optimization for many years. Every automated decision and every optimization run leaves a record of what we decided, what happened next, and what we learned from it. Over time that has built up into a huge amount of data, and that data, more than any one codebase, now defines how our software behaves.

Regenerated, not edited

Look at how a machine learning or reinforcement learning system changes over time. Nobody opens the weights and edits them. Every quarter, or every year, we regenerate them from the historical data that has built up since the last run.

In that loop, the model file is not the real asset. The real assets are the data and the recipe that turns the data into weights. If you lost the weights but kept the data and the recipe, you could rebuild them. If you kept the weights but lost the data, you would have a system you can no longer improve, explain, or reproduce.

That is exactly the relationship between a cache and its source of truth. The weights are a cached, distilled form of the historical data. They are fast to query and much smaller than the data, but they are a derived artifact. You throw them away and rebuild them when the source changes.

The cache inversion

In traditional software, the arrow points the other way. Software is the source of truth, and data is the cache. We memoize function results. We build materialized views so we do not have to run the same query again. We put computed pages on a CDN. The computation is primary, and data saves us from repeating it.

That arrangement strains when the data gets big enough. Take operational logs. Ours are so large that no engineer, and no single query, can hold them in view. To get value from them, we have to distill them: into aggregates, into a minimized summary, or into the weights of a neural network that has learned the patterns. Inference on those weights, which is what Software 3.0 does all day, is then a fast lookup into a compressed form of all that data.

In Software 1.0, data is a cache of computation. In Software 2.0 and 3.0, computation is a cache of data.

The inversion is useful because the vocabulary of caching transfers directly, and it tells us which problems to expect:

Caching conceptWhat it means when the model is the cache
Source of truthThe data and the training recipe, not the weights
InvalidationRetraining, re-distilling, or refreshing the context
Staleness and TTLDrift: the world moved on since the last training run. A retraining cadence is a time-to-live.
Cache missAn input outside the training distribution. The model answers anyway, with confidence, which a real cache never does.
Lossy compressionDistillation keeps the common patterns and drops the rare ones. Rare cases are where the bugs hide.
Cache poisoningBad or biased data in the source flows straight into behavior

The cache-miss row is the dangerous one. A key-value cache tells you when it does not have the answer. A distilled model does not. That is one reason the next two points matter.

The explicit model stays

None of this means we can retire traditional software. Code that explicitly models the dynamics of a system is still very useful, and we cannot do without it. That covers code for how inventory moves, how queues build up, how capacity limits throughput, and how a decision today changes the state tomorrow. It does three things a model distilled from data cannot:

  • It extrapolates. An explicit model of the dynamics gives a reasonable answer for a situation that has never happened, such as a new constraint or a spike larger than any in the history. A distilled model only interpolates between the cases it has seen.
  • It enforces hard constraints. Some rules must hold every time, not 99.99% of the time. Those belong in code that you can test thoroughly or prove.
  • It explains itself. When an explicit model gives a surprising answer, you can trace why. When weights give a surprising answer, you mostly cannot.

So the inversion is a trend, not a replacement. The systems that work best for us combine the two. The explicit model of the dynamics sets the structure and the hard limits. The parts distilled from data fill in what is too large or too fuzzy to write by hand. For each part of a system, the useful question is which way its arrow should point.

Data is the spec

If behavior comes from data, you cannot fully define or check it by reading code. Reading a model’s weights tells you nothing useful. Even for Software 1.0, the code that matters more and more is code that an agent wrote, and humans review it by outcome, not line by line.

So we increasingly define software by how it behaves on a broad, end-to-end set of data, and not by its static code. The definition of “correct” moves from the source file to the dataset:

  • Evaluation sets are specs. For a model or an agent, the eval set is the most precise statement of what we want. Change the eval set, and you have changed the requirements.
  • Production data is the widest test. Replaying real traffic covers the interactions no one thought to write a test for. I wrote about this in Two Ways to Verify Software: tests are behavior samples, and the best samples come from production.
  • End to end beats unit, when the unit is learned. A model has no meaningful unit boundary. The useful test is the full path: real input, through every model and service, to the outcome the customer sees.

This also closes the loop on the cache miss. Wide, realistic behavioral data is how we find the inputs where the distilled model is confidently wrong, before customers find them.

Data as a first-class citizen

Once we accept that data defines the software, the biggest consequence is a change in what we treat as an asset. We have always treated the codebase as a core asset: we version it, review it, protect it, and invest in it. Data that defines behavior deserves the same standing. It is a first-class citizen, not a by-product of running the software.

So the engineering discipline has to cover the data, not only the code. These are the changes we are making:

  1. Collect more data, on purpose, beyond the codebase. Record each automated decision with its context and the outcome that followed. Keep production traffic so we can replay it. Capture every time a human corrects a model or an agent, because each correction is a labeled example. Data you did not collect cannot teach the next version anything.
  2. Version the source, not only the artifact. A release is code, plus the data snapshot, plus the training recipe, plus the prompts and context. If any one of them is missing, you cannot reproduce the behavior.
  3. Set a freshness goal for every distilled artifact. Every model, summary, and knowledge base has a time-to-live, even if nobody wrote it down. Write it down and alarm on it.
  4. Treat regeneration as routine maintenance. Retraining and re-distilling are non-functional work with a mechanical success check: the eval set passes and drift goes down. That makes them a natural job for the self-maintenance stream I described in Slice by Intent, Not by Phase. Agents should run them on a schedule, not on someone’s memory.
  5. Review data changes like code changes. A change to the training data or the eval set changes behavior as surely as a code change does. It deserves the same review, and the same rollback path.
  6. Keep lineage. When a behavior looks wrong, the question is “what data taught it this?” You can only answer that if you can trace from the artifact back to its sources.

Code that models how a system behaves is not going away. But more and more of what our software does comes from data, and that makes the data as much a part of the software as the code. Treat it that way: collect it on purpose, version it, review it, and keep the models built from it fresh.
