Stateless Apps, Central Data: What the Agentic Ecosystem Is Missing

Apps are cheap to build now. Their state is not. Documents, agent memory, and heavy capabilities like speech-to-text should live on one shared, governed floor, and every app should be a replaceable view on top of it.

1,800 words~7 min read2026-11-17

In short

  • With agents, building an app takes days. Storing its data safely still takes weeks, so most new apps skip that part.
  • Every app has two halves: a stateless experience (UI, agent, prompts) that is cheap to replace, and stateful data that is expensive to lose.
  • The agentic ecosystem rebuilds the stateful half in every app. Documents are one symptom. Fragmented agent memory, and a 0.5 GB speech-to-text download for each app, are two more.
  • The fix is one shared floor: central documents, central memory, and shared capabilities, governed and paid for once.
  • On top of it, apps become views. Anyone can build a better one, and retiring one loses nothing.

Apps are cheap now. State is not.

Every application has two halves, and they carry different risks:

  • The experience is stateless. UI, HTML pages, client scripts, agents, and prompts. It is cheap to build and cheap to throw away. If one breaks or is abandoned, a new one can replace it.
  • The data is stateful. Documents, diagrams, reviews, records, and whatever users type in. It is expensive to recreate, often sensitive, and valuable long after the app that made it is gone.

Agents made the first half almost free. A team can now build a new editor, viewer, or dashboard in days. But each new app still has to decide where its data lives, and the quickest answer is “in a database in our own cloud account.” So that is what most apps do.

Some apps already get this right. A static viewer that reads files straight from the company’s Git server, as the signed-in reader, has no storage of its own. Its data inherits Git’s permissions, history, code review, and ownership. If the viewer disappears, nothing is lost.

Symptom 1: documents locked inside each app

Document apps are where this hurts most: tools whose main data is what people write, such as docs, diagrams, threat models, and reviews. When each one keeps its documents in its own store, two things go wrong.

Use comes before review. Nobody outside the team knows what data the app holds, how it is classified, who can read it, or whether it is encrypted and retained correctly. A useful app spreads across teams in weeks. The security and privacy review, if it happens at all, comes later. By then, other teams’ data is already in it. And because every app rebuilds access control, every app makes its own mistakes.

The data dies with the app. Teams reorganize, and owners move on. The data is tied to the app’s account, schema, and UI. Users can read it one item at a time while the app still runs, but there is often no way to export it in bulk. Most large organizations have lived through this: a tool that many teams used for diagrams or threat models is retired, and its users find out that export works one item at a time.

Editors show the same problem from the other side. When a popular document editor is retired, several successors appear, each with its own storage. Users pick one, migrate their documents, and migrate again if that one is retired too. The documents are the same every time. Only the editor changes.

Symptom 2: fragmented memory

Agents have the same problem with memory. Each agent tool keeps its own: one in the IDE, one in the command line, one in the chat app, one per person, and one per machine. Each one learns the same facts about the team’s systems on its own, and none of them can see what the others learned. When you switch tools, the memory stays behind. When the tool is retired, the memory goes with it.

In Agent Memory Is a Team Document, I argued that the knowledge worth keeping belongs in documents the whole team can read. This is the storage half of that argument. Memory is data, so it needs the same floor as documents: one central store, owned by the team, that every agent reads and writes as the signed-in user. A tool can cache what it needs. The canonical memory lives outside it.

Symptom 3: every app ships its own heavy capabilities

The third symptom is about capabilities, not data. Many agent apps now offer voice input, and each one asks you to download its own speech-to-text model: about 0.5 GB each, in our experience. Install five of these apps and you have 2.5 GB of what is mostly the same model, five update cycles, and five copies of a component that somebody has to patch.

That is the same mistake one layer down. A capability that every app needs should be installed once and shared, the way an operating system provides fonts, a keyboard, or a camera. Apps call it through a stable local API. They do not each bring their own.

One diagnosis

Documents, memory, and capabilities look like three different problems. They are one: every app rebuilds the parts it should share. Data, memory, and heavy dependencies are expensive, long-lived, and need governance. The UI and the agent are cheap and short-lived. We keep bundling the two together, so the expensive part inherits the short life of the cheap part.

The proposal: one contract, open experiences

The fix has two parts.

1. Put state behind one contract, not one database. Every document, memory, and dataset has a canonical copy in an open format, in a governed store. The store owns access control, classification, encryption, audit, retention, and export, so each app does not have to. Ownership belongs to an org, not to the app or the person who built it, so it survives a reorg.

Editors can still keep their own working state next to the canonical copy, such as a CRDT log for live co-editing or a table of locks. The contract only asks that the canonical copy is saved in an open format and kept current, so it outlives the editor.

2. Leave the experience layer open. Anyone can build a UI, a dashboard, or an agent on top of the shared floor, with no storage design and no storage review. Apps become views over the data, and they can be replaced when better ones appear. Two editors can still differ in how they edit. One may show live cursors and the other may not. Those features may not carry across, but the document always does.

This also makes reviews much smaller. To review a stateless app, you check what it displays and which permissions it asks for. That is a fraction of the work of reviewing a full stack.

What the shared floor must provide

CapabilityRequirement
Identity and accessEvery read and write is made as the signed-in user and checked against existing groups and permissions. No shared service credentials to the data.
ClassificationEach dataset is classified when it is created, and the classification decides which controls apply.
ProtectionEncryption at rest and in transit, access logs, and retention and deletion that follow policy.
OwnershipEach dataset has an owning org, so a reorg gives it a new owner instead of orphaning it.
PortabilityBulk export and import in an open format. Retiring an app includes a migration path for its data.
InventoryOne searchable list of which apps use which data, for reviewers and for owners.
Shared capabilitiesHeavy components such as speech-to-text are installed once, versioned, and called through a stable API.
Builder experienceA simple client API and templates, so using the floor is faster than setting up your own account.

Let browser apps read the source directly

One small change unlocks many stateless apps. Many internal Git servers send no CORS headers, so a browser app on another internal origin cannot read a file, even with the user’s own session. The workarounds are a browser extension or a backend proxy. A proxy has to hold read access of its own, which bypasses each user’s permissions.

The fix is narrow. On read-only raw-file endpoints, send CORS headers for an explicit allowlist of internal origins, with credentials allowed. Every read is still made as the signed-in user and checked against that user’s permissions, so no new access is granted. Writes stay out of scope and keep going through code review.

How to get there

  1. Inventory. Find the apps that keep their own documents, memory, or heavy capabilities, and rank them by data sensitivity and number of users.
  2. Pave the path. Choose or build the shared store, publish its client API and app templates, and get its controls approved once.
  3. New apps first. Require new apps to use the floor, with an exception process for workloads it cannot serve, such as very high throughput or very large objects.
  4. Migrate by risk. Move the highest-risk apps first. Starting now, make bulk export a required step in every app retirement.

Some questions are still open. Which canonical format fits each type of document: Markdown or HTML for docs, .drawio for diagrams, a structured format for threat models? How often should an editor with live co-editing write its canonical copy: on every save, every few seconds, or when a session ends? And how are the store and the shared capabilities funded? None of these is a reason to wait. Each app that launches on its own storage makes the migration bigger.

Agents will keep making apps cheaper to build. That is good news, but only if the part that matters does not also get cheaper to lose. Put documents, memory, and heavy capabilities on one shared floor, and let the apps on top compete on the experience. Then retiring an app is a non-event, a new app can launch with most of its review already done, and you download the speech model once.
