Slice by Intent, Not by Phase: Organizing a Software Factory Around Three Change Streams

We used to drive AI adoption one phase of the development lifecycle at a time. It helped, but it was slow. Organizing the work by what triggered each change shifted mindsets much faster, and it helped us reach a 2x productivity increase.

2,400 words~10 min read2026-11-12

In short

  • We used to drive AI adoption one SDLC phase at a time. Each phase got faster, but changes did not reach production much faster.
  • Now we organize work by what triggered each change: a feature request, a production signal, or the health of the code.
  • Each of these three streams gets one goal, placed on the step where it usually gets stuck.
  • Agents should fully own non-functional work. Humans own the intent, the functional requirements, and the guardrails.
  • The system, not each engineer, runs the agents, through one team-level agent. The result so far: a 2x productivity increase.

How we used to do it

When we started driving AI adoption, we did what most teams do. We split the software development lifecycle (SDLC) into phases and gave each phase an owner:

  • Operations: oncall agents, smarter alarms, ticket triage.
  • Development: spec-driven development, AI code review, continuous delivery.
  • Knowledge base: AGENTS.md files, steering docs, wiki sync.

It helped. Alarms got less noisy, ticket volume went down, and other teams adopted the regression tests we built from production traffic.

But it was not efficient. Each owner made their own phase faster, and the total time barely moved. A faster code review did not help a fix that then waited two days to deploy. A better knowledge base did not help a feature stuck in three meetings about what to build.

We also found three deeper problems:

  1. Production feedback did not reach development. Operations was the last phase. Alarms and tickets were closed there, and they never went back to development as signals about where the software is fragile. The same issues kept coming back. We got faster at closing them, not at removing them.
  2. Nobody owned keeping the code evergreen. No phase owns upgrades, security patches, or complexity reduction, so nobody expected a mechanism to do them continuously. They happened only when someone had time, or when a deadline forced them.
  3. All work started with a feature request. If development means “someone asks for a feature, then we build it,” work that nobody asks for gets ignored. Self-maintenance never has a requester, so it dropped out of the picture.

All three come from one blind spot. A phase plan shows how a change moves through the lifecycle, but not where the change comes from. AI makes this worse. As writing and reviewing code gets faster, the bottleneck moves away from the code, and where it moves depends on the kind of change.

Start from intent, not from phase

So we started again from first principles. We set the SDLC aside and asked one question about every change: what triggered it, and what is it trying to achieve? The answers fall into three streams:

  1. Features (business intent). Someone wants the software to do something new, or to behave differently.
  2. Operational feedback. Production tells us something is wrong: an alarm, a ticket, a defect. The signal itself carries the intent. We want AI to fix these automatically.
  3. Self-maintenance (non-functional requirements). Nobody asks for it, but the code still has to change: upgrades, security patches, complexity reduction, dead-code removal. This keeps the code in a state where agents can keep working on it.

These are the same three streams as in Software Factories for Brownfield Code at Amazon Scale. That post covers how each stream works. This post covers how we used them to organize the transformation itself: the goals, the level of autonomy, and who runs the agents.

Instead of slicing the lifecycle by phase, we slice it by trigger. Each stream runs end to end and has one velocity goal:

StreamTriggerVelocity goal
1) FeaturesBusiness intentFeature description → agreed spec in < 2 hours; → first experiment results in < 1 week
2) Operational feedbackProduction signalIssue raised → fix deployed to production in < 2 hours
3) Self-maintenanceHealth of the codeComplexity goes down every quarter; each change lands in < 2 hours

This new view changed mindsets faster than any tool we rolled out. Engineers stopped asking “how do I use AI in code review?” They started asking “why does this kind of change take a week, and what is holding it up?”

The results followed. Our team has achieved a 2x productivity increase. Working by phase gave us small gains in each phase. Working by stream let those gains add up from end to end.

Match AI autonomy to how clear the intent is

The streams differ in one way that matters a lot for AI: how clear the intent is. The clearer the intent, the more autonomy an agent can have.

StreamHow clear is the intent?AI’s roleWhere it gets stuckWhat we measure
FeaturesUnclear until humans agree on itSpeeds up the build once the spec is agreedAt the start: agreeing on a specTime to agreed spec, then to first experiment results
Operational feedbackClear: the signal says what is wrongFixes issues, and each fix makes the system strongerAt the end: deploying safelyTime to production deploy
Self-maintenanceClear: success can be checked mechanicallyWorks on its own, inside guardrailsIt never gets prioritized, because nobody asks for itComplexity trend

Why the difference? It comes down to feedback. Marc Brooker calls this the feedback loop hypothesis in What’s Easy Now? What’s Hard Now?: what an agent can do is limited by how much accurate feedback it gets. If a change can check itself with tests, evals, or regression suites, an agent can run it with a lot of autonomy. If success depends on how customers react, you need a production experiment, and a human has to make the call.

Stream 1: Features, where humans own the intent

For features, the delay is at the start. Once there is a clear spec, AI makes the build cheap. Getting to that spec is human work: agreeing what to build, with whom, and how we will know it worked.

Our goals:

  • Feature description → agreed spec in under 2 hours.
  • Feature description → first experiment results in under 1 week.

To keep the numbers honest, we sort features into three cases:

  1. Straightforward. The intent and the existing context are enough. AI drives it end to end, with humans aligned.
  2. Algorithm change. The same 2-hour spec goal, plus a separate formal verification step that proves the algorithm does what the spec says.
  3. Needs more input. It waits on upstream data or another team’s decision. That wait is taken off the clock. We confirm the data exists when we write the spec, not halfway through the build.

Large projects are not exempt. A big release needs too many judgment calls to go through the factory as one piece. But it is made of many small deliveries, and many of those fit. Humans decide how to split it and make the judgment calls. The factory builds the well-defined pieces. If only a few pieces fit, the project needs a better split.

Stream 2: Operational feedback, where the signal is the spec

An operational issue comes with its intent attached: make the alarm stop. The fix is usually small. The hard part is getting it to production safely. A merged fix does not close the issue. Only the deploy that clears the signal does.

Our goal: issue raised → fix deployed to production in under 2 hours. That does not mean skipping bake time or approvals. It means building pipelines where a small fix can pass every safety check in that time (see small, continuous changes). Where a pipeline cannot do that, the gap becomes the next thing to improve.

But do not just get faster at closing the same ticket. Each issue shows where the software is fragile. So we treat each issue as a router: fix this instance, then send the root cause to the right kind of change.

  • A missing alarm, retry, timeout, or permission becomes an infrastructure-as-code change, so every environment gets the fix.
  • Tangled code that keeps breaking goes to the self-maintenance stream for refactoring.
  • A brittle boundary between services gets a better interface, not a workaround on one side.

We pair the speed goal with a check for repeat issues. The goal is better software, not just faster ticket handling.

Stream 3: Self-maintenance, where agents do the work

The brownfield post explains why a factory that only ships features decays. What changed for us was how much autonomy to give agents here.

Nobody outside the team asks for non-functional work, so it always loses to features and incidents. But its success is easy to check, so it does not need a human in the loop. An agent needs two checks that it can run on its own:

  • Did complexity go down? A complexity score answers this.
  • Did behavior stay the same? A regression suite answers this.

With both in place, the agent picks a hotspot, restructures it, runs both checks, and sends the change for review. Nobody has to start it.

Two rules keep this honest. We measure the outcome (complexity goes down every quarter), not the number of changes. And we report complexity added by features separately from complexity removed by refactoring. A guardrail keeps each change under 2 hours from hotspot to merge.

This already works at small scale. One of our agent pipelines opened two code reviews on its own. They removed catalog entries that pointed at deleted skill files. Nobody asked for them. Next, we want business events to trigger cleanup. When a line of business moves out of a system, the deprecation notice or the drop to zero traffic should start jobs that remove the dead code, configs, and tests. Humans review the removal. They should not have to remember to start it.

Agents will own non-functional work

We discussed this model with several senior principal engineers at Amazon, and we agreed on one conclusion: agents will fully handle non-functional requirements. Upgrades, security patches, complexity reduction, outdated docs, and dead code are all well defined, easy to check, and never finished. Agents are good at this kind of work. Humans are bad at making time for it.

That changes the human job. Humans provide three things:

  1. Intent: what the software should do, and why.
  2. Functional requirements: an agreed spec that makes the intent buildable.
  3. Guardrails: regression tests, verification steps, review rules, and deployment safety checks. These let the factory act on its own without breaking production.

Everything else is the factory’s job. The most important part to define is the self-maintenance mechanism: what runs, how often, how it is measured, and which guardrail stops it.

Let the system run the agents

The second big shift is about who manages the agents.

In the first wave, humans managed them. Each engineer had their own agent. They started it, watched it, checked its output, and remembered what to run next. That is AI-assisted development: the agent does tasks, but a person is still the workflow engine.

A factory flips this. The system manages the workflow, not the humans. Triggers start the work: a new spec, an alarm, a complexity threshold, a schedule. The system sends each change to the right stream, runs the checks, and asks a human only when judgment is needed. Humans stop watching agents and start reviewing results.

This matters because the mix of work is changing. Only one stream, features, starts with a person asking. The other two are triggered by the system: an alarm, a ticket, a new dependency version, a complexity score, a schedule. As agents take over non-functional work, these two streams grow the fastest. Soon, most code changes will be triggered by the system, not by humans. A workflow that waits for a person to start each change cannot keep up.

That is the move to AI-native development. In an AI-native team, everyone works with one team-level agent instead of their own personal agent. The team agent holds the team’s context, rules, and history. When one engineer corrects it, the whole team benefits on the next run. Ten personal agents give you ten slightly different versions of the team’s practices. One team agent gives you one version, and it gets better every week.

Personal skills got most of us fluent with agents over the past year. But personal skills depend on someone remembering to run them. So we moved the practice to the team level:

  • Team-owned scheduled jobs. A central scheduler runs team jobs daily or weekly. We started with auto-refactor, doc sync, release notes, and retrospectives.
  • Retrospectives as scheduled analysis. Much of a retro is the same analysis of data we already have. Which review rules fire, and which get accepted? Where is the bottleneck on the way to production? Where did a human have to step in? That last question is the factory’s own backlog, because each step-in points to the next thing to automate.
  • Team-hosted agents. Local agents are still great for exploring. Team-hosted agents apply the team’s practices the same way every time, so every improvement benefits everyone.

We also changed how we plan. If sprint planning only schedules features and fixes, factory work gets crowded out. So most of our capacity now goes to the factory itself: “automate step X,” “make Y check itself,” “reduce complexity in hotspot Z.” For every manual task, we ask: what part of the factory should have done this, and can we build that instead?

Is the output worth shipping?

Lead time shows how fast the factory runs, not whether its output is good. A factory that opens many code reviews that never ship looks busy and wastes reviewers’ time. So we track quality next to speed:

MetricWhat it measuresWarning sign
Merge-to-production rateShare of changes that are merged and deployed, not abandoned or revertedLow: specs are unclear, or the agent’s own checks miss what reviewers catch
Change failure rateShare of deployments that cause a rollback, a revert, or an operational issueHigh: the checks miss real defects
Rework per changeRevisions and blocking comments before mergeHigh: the agent lacks context, so humans fix its work by hand

We report agent-written and human-written changes separately, to check that the factory’s output meets the same bar.

Where this leaves humans

The human role does not shrink in this model. It moves up: from writing each change to defining intent, agreeing on specs, and designing the guardrails and self-maintenance that let the factory run. That work is harder and more valuable, and senior engineers are best placed to lead it.
