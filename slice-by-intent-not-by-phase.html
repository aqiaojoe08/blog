Slice by Intent, Not by Phase: Organizing a Software Factory Around Three Change Streams

We used to drive AI transformation one SDLC phase at a time. It helped, but it was slow. Organizing the work by what triggered a change, and what it is trying to achieve, changed minds much faster.

2,600 words~11 min read2026-11-12

How we used to do it

When we first drove AI adoption across our team, we did what most engineering organizations do. We cut the software development lifecycle into phases and gave each phase an owner. One person drove AI for operations: oncall agents, smarter alarms, ticket triage. Another drove AI for development: spec-driven development, agent-assisted code review, continuous delivery. A third owned the knowledge base: AGENTS.md files, steering docs, wiki sync.

It worked, up to a point. Each phase got measurably better. Alarms got less noisy, ticket volume went down, regression testing built from production traffic became a template other teams adopted, and we planned a productivity gain into our annual plan.

But it was not efficient. Phase owners optimized their own phase. A faster code review did nothing for a fix that then waited two days in a deployment pipeline. A better knowledge base did nothing for a feature whose real delay was three meetings to agree on what to build. Every phase got faster, and the time from “we need this” to “this is in production” barely moved. Engineers kept treating AI as tools bolted onto the old process, not as a reason to change the process.

The underlying problem: as AI raises the speed of writing and reviewing code, the bottleneck moves away from the code. Where it moves depends on the kind of change. A per-phase plan cannot see that, because every kind of change flows through the same phases.

Working backwards from intent

So we started over from first principles. We set the SDLC aside and asked one question about every change: what triggered it, and what is it trying to achieve? The answers fall into three streams:

  1. Business intent (features). Someone wants the software to do something new or behave differently: a new capability, a new decision the system can make, a new customer-facing behavior.
  2. Operational feedback. Production is telling us something is wrong. An alarm fired, a ticket was cut, a defect surfaced. This is not a new requirement; the signal itself carries the intent. These are the signals we want to automate, with AI fixing the bugs.
  3. Non-functional requirements (self-maintenance). Nobody outside the team asks for it, but the software has to keep changing anyway: dependency and runtime upgrades, security patches, complexity reduction, dead-code removal. This is the work that keeps the code base in a state where agents can keep working on it.

If these look familiar, they are the same three streams from Software Factories for Brownfield Code at Amazon Scale. That post covered what each stream’s loop looks like, and the shared primitives, maintenance loop, and small changes that make them work on large systems. This post is about something else: using the streams to organize the transformation itself, set a goal for each one, decide how much autonomy each one gets, and decide who runs the agents.

We stopped slicing the lifecycle vertically by phase and started slicing it horizontally by trigger. Each stream runs end to end, from its own trigger to production, and each gets one velocity goal on the stage that actually gates it:

StreamTriggerVelocity goal
1) FeaturesBusiness intentFeature description → agreed spec in < 2 hours; → first lab readout in < 1 week
2) Operational feedbackProduction signalIssue raised → fix deployed to production in < 2 hours
3) Self-maintenanceEngineering healthComplexity trends down every quarter; each change lands in < 2 hours

This framing did more for the mindset shift than any tool we rolled out. Engineers stopped asking “how do I use AI in code review?” and started asking “why does this kind of change take a week, and which stage is holding it?”

Match AI autonomy to how ambiguous the intent is

The three streams differ in one property that matters a great deal for AI: how ambiguous the intent behind the change is. That sets how much autonomy an agent should get.

StreamIntent ambiguityAI’s roleWhere it gets stuckWhat we measure
FeaturesHighAccelerator, after humans align on intentThe front: reaching an agreed specTime to agreed spec, then to lab insights
Operational feedbackLow (the signal supplies the intent)Compounding flywheelThe back: the deployment gateTime to production deploy

The deeper reason the gates differ is the feedback loop each change gets. Marc Brooker calls this the feedback loop hypothesis in What’s Easy Now? What’s Hard Now?: the availability of accurate feedback sets the limit on what agents can do. A change that can verify itself inside your own pipeline (tests, evals, regression suites) can run at high autonomy. A change whose success depends on customer behavior needs a production experiment, and a human has to own the judgment.

Stream 1: features, where humans own the intent

For a feature, the delay lives at the front. Once there is a crisp, buildable spec, AI makes implementation cheap. Getting to that spec is human work: agreeing what to build, with whom, and how we will know it worked.

So the primary goal is feature description → agreed spec in under 2 hours, and the secondary goal is feature description → first lab readout in under a week. To keep the metric honest, we split features into three cases:

  1. Straightforward. The intent plus existing context is enough. AI drives it end to end with human alignment.
  2. Algorithm change. Same 2-hour spec target, plus a separately tracked formal verification gate that proves the algorithm behaves as specified.
  3. Needs more input. Upstream data, another team’s decision, a missing dependency. The wait for that input is taken off the clock, and data availability has to be confirmed at spec time, not discovered mid-build.

A slow case-3 feature is then visibly a dependency problem. It does not look like slow spec drafting.

Large projects are not exempt. A big release cannot run through the factory as one unit, because it needs too many judgment calls. But it is made of many small deliveries, and many of those pieces do fit. Humans own the split and the judgment calls; the factory carries the well-defined pieces. We track the share of each large project’s deliveries that qualify for the fast path. A low share means the project needs a better split.

Stream 2: operational feedback, where the signal is the spec

An operational issue arrives with its intent already attached: make the alarm stop firing. The fix is usually small. The delay is getting it safely to production. A merged fix does not close an issue; only the deploy that clears the signal does.

So the goal is issue raised → fix deployed to production in under 2 hours. That does not mean skipping bake time, approvals, or blocked days. It means building pipelines where a small, incremental fix can pass every safety gate in that window (see small, continuous changes). Where a pipeline cannot, that gap is the next improvement item.

We also learned not to over-optimize this stream. Getting faster and faster at resolving the same recurring ticket is a trap. Each issue is a signal about where the software is fragile, so we treat an issue as a router: clear the instance, then send the root cause to the right kind of change.

  • Operational gaps (a missing alarm, retry, timeout, or permission) become an infrastructure-as-code change, so every environment inherits the fix and it cannot quietly reappear.
  • Tangled code that keeps breaking goes to the self-maintenance stream for refactoring.
  • Brittle service boundaries call for re-architecting the interface, not a workaround on one side of it.

Speed to deploy matters because it shortens the feedback loop. It is a means to a more robust system, so we pair it with a recurrence check. The goal is to improve the software, not just our ticket handling.

Stream 3: self-maintenance, where agents should do the work

The brownfield post explains why a factory that only ships decays, and the maintenance loop that stops it. What changed in our thinking was the level of autonomy. Non-functional work has no external customer pulling it, so it always loses priority to features and incidents. But its success is mechanical, so it does not need a human in the loop. It needs two checks an agent can run on its own: a complexity score that should go down, and a regression suite that should still pass. With both in place, the agent picks a hotspot, restructures it, and sends it for review. Nobody has to start it.

Two rules keep the goal honest. The goal is the outcome (complexity trends down every quarter), not the number of refactoring changes, and complexity added by feature work is reported separately from complexity removed by refactoring, so feature growth does not hide progress. A guardrail caps each change at 2 hours from hotspot to merge.

This already works at small scale. One of our agent pipelines opened two code reviews on its own that removed catalog entries pointing at skill files that no longer existed. Nobody asked for them. The next step is to let business events trigger cleanup: when a line of business moves out of a system, the deprecation notice or the drop to zero traffic should start the jobs that remove the dead code paths, configs, and tests. Humans review the removal. They should not have to remember to start it.

Agents will own non-functional work

We discussed this model with several senior principal engineers at Amazon and came away aligned on one conclusion: non-functional requirements will be handled fully by agents. Dependency upgrades, security patches, complexity reduction, documentation drift, dead-code removal: all of it is well defined, mechanically verifiable, and continuous. That is the profile of work agents are best at and humans are worst at prioritizing.

That changes the human job. Humans provide three things:

  1. Intent: what the software should do and why.
  2. Functional requirements: the agreed spec that makes intent buildable.
  3. Guardrails: the regression tests, verification gates, review rules, and deployment safety checks that let the factory act on its own without breaking production.

Everything else is the factory’s job. The most important part of the factory to define is its self-maintenance mechanism: what runs, on what cadence, measured by what, and stopped by which guardrail.

Let the system run the agents

The second big shift is about who manages the agents. In the first wave of adoption, humans tracked the agents. Each engineer had their own agent, started it, watched it, checked its output, and remembered what to run next. That is AI-assisted development: the agent does tasks, and a person is still the workflow engine.

A factory inverts this. The system manages the agentic workflow, not the humans. Triggers start the work: a new spec, an alarm, a complexity threshold, a schedule. The workflow routes each change to the right stream, runs the checks, and asks a human only at the points that need judgment. Humans stop babysitting agents and start reviewing outcomes.

That is the move from AI-assisted to AI-native development. In an AI-native team, every team member works with a single team-level agent, instead of each person running a separate agent of their own. The team agent carries the team’s context, rules, and history. When one engineer corrects it, the whole team benefits on the next run. Ten personal agents give you ten slightly different versions of the team’s practices; one team agent gives you one, and it gets better every week.

Self-maintenance on a cadence only works if something actually runs it on that cadence. Over the past year most of us built real fluency with agents through local, personal skills. That was the right first step, but personal skills depend on a person remembering to run them. The next step is to bring the practice back to the team level:

  • Team-owned scheduled jobs. A centralized scheduler runs team jobs daily or weekly instead of waiting for someone to trigger them. The chores from the brownfield post’s maintenance loop now run as team jobs, not personal ones. We started with auto-refactor, doc sync, release notes, and retrospectives.
  • Retrospectives as scheduled analysis. Much of an ops review or sprint retro is recurring analysis over data we already have. Which review rules fire and get accepted? Where is the bottleneck in time to production? At which steps did a human have to step in? That last question is the factory’s own backlog, because every human intervention names the next piece of automation.
  • Remote, team-hosted agents. Local agents stay great for exploration. Team-hosted agents apply the team’s practices the same way on every run and build up shared knowledge, so each improvement benefits everyone. That compounding is what a factory depends on.

We also changed how we plan. If sprint planning keeps scheduling individual features and fixes, the backlog fills with traditional work and factory work gets crowded out. So most committed capacity now goes to the machine: “automate stage X,” “make Y self-verifying,” “reduce complexity in hotspot Z.” Every traditional task becomes a question: what part of the factory should have produced this automatically, and can we build that instead?

Is the output worth shipping?

Lead time shows how fast the factory runs. It does not show whether the output is good. A factory that opens many code reviews that never reach production looks busy and wastes review time. So we track quality next to velocity:

MetricWhat it measuresWarning sign
Merge-to-production rateShare of opened changes that are merged and deployed, not abandoned or revertedLow: specs are unclear, or the agent’s self-checks miss what reviewers catch
Change failure rateShare of deployments that cause a rollback, revert, or operational issueHigh: the gates miss real defects
Rework per changeRevisions and blocking comments before mergeHigh: the agent lacks context, so humans correct it by hand

We report agent-authored and human-authored changes separately, so we can see whether the factory’s output meets the same bar.

What we learned

  • Slice by intent, not by phase. Phase owners make phases faster. Stream owners make changes faster, because each stream’s goal sits on the stage that actually gates it.
  • Let the feedback loop set the autonomy. High-ambiguity work keeps humans in charge of intent. Mechanically verifiable work should run on its own.
  • Put the goal on the gate. Each stream stalls somewhere different: features at the spec, fixes at the deploy, maintenance at prioritization. Measure there.
  • Hand non-functional work to agents. Humans own intent, functional requirements, and guardrails.
  • Let the system manage the agents. Move from one agent per person, tracked by hand, to one team-level agent driven by triggers and schedules. If upkeep depends on someone remembering, it will not happen.

The human role does not shrink in this model. It moves up: from writing each change to defining intent, agreeing specs, and designing the guardrails and self-maintenance mechanisms that let the factory run. That work is harder and more valuable, and it is the work senior engineers are best placed to lead.
