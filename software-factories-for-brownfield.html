Software Factories for Brownfield Code at Amazon Scale

Agentic software factories are not only for greenfield apps and small teams. To make them work on large, old code bases, you need three things: shared primitives, self-maintenance, and a habit of small, continuous changes.

2,500 words~11 min read2026-10-11

The objection

A software factory is a repeatable loop where agents take an idea through spec, code, test, and release, and humans review the parts that matter. Demos of this loop look great. An agent builds a to-do app, a dashboard, or a new microservice from a prompt, and it works.

Then someone who owns a ten-year-old system with millions of lines of code, dozens of upstream feeds, and a pager asks the fair question: does this work for us? The usual answer is no. Factories are for greenfield work and small or mid-sized projects. Large brownfield systems are too tangled, too risky, and too hard to fit in an agent’s context.

At Amazon scale, most of the code that matters looks like that system. If factories only work on greenfield projects, they miss most of the work.

I think that answer is wrong, but the objection points at something real. It is worth asking why factories work on small projects, because that tells us what to build for large ones.

Why factories work on small projects

Small projects have three properties that agents depend on:

  1. The context fits. The agent can read the parts of the code it needs and hold them in view. Nothing important hides in another repo or in someone’s head.
  2. Feedback is fast. Building and testing take minutes. The agent can try, fail, and fix in one session.
  3. The blast radius is small. A bad change breaks one thing, and it is easy to see and roll back.

Large brownfield systems lose all three. The context is spread across many services. End-to-end testing takes days and needs people from several teams. A bad change can reach customers, partners, or money.

So the goal is not to give up on large systems. The goal is to bring those three properties back. Each of the three ideas below restores one or more of them.

1) Break down complexity with shared primitives

Most large systems are not one big problem. They are several mid-sized applications that keep rebuilding the same hard parts: getting clean input data, replaying past decisions, explaining why the system did what it did, and remembering how the pieces connect. Each team builds its own version, each version drifts, and every agent session has to learn all of it again.

The fix is to pull those hard parts out into a small set of common primitives, owned once and used by everyone. Four primitives cover most of it:

  1. Data. One place to get inputs, both live and as they were at any point in the past. If every application reads the same inputs the same way, a whole class of “your numbers don’t match mine” bugs goes away.
  2. Testing and evaluation systems. A test environment that lets you run end-to-end tests as much as possible, without waiting for production or for other teams. One kind of test is not enough, because different systems fail in different ways:
    • Unit and contract tests check one module, and the interfaces between modules, in seconds.
    • Replay and regression tests run the old and new code on the same recorded inputs and compare the outputs.
    • Gyms for RL and optimization systems simulate the world the system acts on, so you can score a policy over many periods before it touches real customers or money.
    • Evals for agentic systems score an agent against a set of tasks with known good answers, using checks, rubrics, or a judge model, and catch regressions when a prompt, tool, or model changes.
    • Online experiments (shadow runs and A/B tests) are the last step, for what offline tests cannot prove.
    This is how an agent tests a change end to end on its own, in minutes or hours instead of weeks.
  3. Explainability. If you can replay a decision, you can explain it. Run the old and new logic on the same inputs, and you can say whether a change in output came from the code or from the inputs.
  4. Knowledge base. A written map of the system: what each part does, who owns it, how parts connect, and which patterns to follow. Agents read it before they work and update it after.

Once these primitives exist, each application on top of them becomes a mid-sized project again. An agent working on one application does not need to understand how data is collected for the whole company. It calls the data primitive. It does not need to build a test environment. It onboards to the shared testing and evaluation systems. The primitives absorb the complexity so the applications don’t have to.

Two rules make primitives safe to share:

  • Share the code, isolate the runtime. A shared primitive that fails can take every application down with it. Let each team run its own instance from a shared code base, so a bad deploy in one place stays in one place. Share a runtime only where sharing is the point, like data.
  • Give each primitive one owner. A primitive with no owner becomes the next legacy system. The owner keeps the interface stable and the docs current.

This is the oldest idea in software, abstraction, applied for a new reason. We used to build abstractions so people could manage complexity. Now they also decide how much context an agent needs to do useful work. AI makes this more valuable, not less: coding is cheap now, so teams can build and maintain primitives that used to be too expensive to justify.

2) Make the system maintain itself

Primitives fix the structure at one point in time. But architecture decays. Every feature leaves something behind: a flag nobody removed, a code path for a customer who left, a copy of a helper that drifted, a dependency two major versions behind. In a large system the decay grows faster than any team can clean it up.

Agents make this worse before they make it better. An agent can add code much faster than a person, and it adds code in the style of whatever it reads. If the code base is messy, the agent copies the mess. If complexity keeps growing, the context problem from the last section comes back.

Three streams of work, not one

Most public writing about software factories talks about one stream of work: features. An idea comes in, and the agent turns it into a spec, code, tests, and a release. That is the stream that demos well. But on a system that has been running for years, features are only part of the work. A factory that runs only the feature stream will add code faster and faster until nobody, human or agent, can work in it.

A brownfield factory runs three streams, each with its own input, loop, and measure of success:

StreamInputLoopSuccess looks like
1) FeaturesIdeas, specs, business asksSpec → code → test → release behind a toggleShorter time from idea to tested result
2) Operational feedbackAlarms, tickets, bug reports, failed runsTriage → find the cause → fix → add a regression test so it cannot come backFewer repeat issues, faster time to fix
3) RefactoringComplexity measures, rule violations, old flags, outdated dependenciesFind the decay → small change → prove no behavior change with regression testsComplexity flat or falling while features keep shipping

Splitting the work this way is what makes self-maintenance executable instead of a slogan. Each stream has a clear input that an agent can watch, a loop it can run, and a number someone can check. “Keep the code base healthy” is a wish. “Every alarm gets a root cause and a regression test” and “every retired flag is removed within two weeks” are jobs an agent can do on a schedule.

The streams also feed each other. Operational feedback finds the gaps in the regression tests. Refactoring keeps the code small enough that the next feature fits in context. And the regression tests from streams 2 and 3 are what make stream 1 safe to run fast.

To keep streams 2 and 3 running, the factory needs a maintenance loop that runs all the time, not a cleanup project every two years. In practice that means:

  1. Agents do the chores. Removing dead code, retiring old feature flags, upgrading dependencies, and merging duplicate helpers are boring, well-defined tasks. They are a good fit for agents, and they should run on a schedule, not when someone has time.
  2. Rules are written down and enforced in the loop. Architecture rules that live only in senior engineers’ heads get broken. Write them as checks that run at every stage, from spec review to code review to deploy: “this table is retired, don’t write to it,” “all new inputs go through the data primitive,” “no new service calls this API directly.” Then agents and humans follow the same rules, and the rules apply across the whole lifecycle instead of only at review time.
  3. Measure complexity and set a budget. Track a few numbers that show decay, like dead code, open flags, duplicate logic, and time to onboard a new application to the testing and evaluation systems. Spend a fixed share of capacity on keeping them flat or falling.
  4. Keep the knowledge base current. When an agent finishes a change, it updates the map. A stale map is worse than none, because agents trust it.

The test of self-maintenance is simple. A year from now, is the code base easier or harder for an agent to work in? If the answer is “harder,” the factory is building its own legacy system.

3) Ship small changes, continuously

The last idea is cultural, and it is the one large teams resist most. Large systems tend to ship in big batches: long-lived branches, quarterly releases, “the migration.” Big batches are bad for people, and they are worse for agents. A big change needs a big context, takes a long time to review, and is hard to test and hard to roll back. It throws away all three properties from the start of this post.

Small changes bring them back. A change that touches one module needs only that module in context. It can be reviewed in minutes and rolled back in seconds. And when changes are small, they can ship continuously, which keeps feedback fast.

Two practices make small, continuous changes safe on a system that cannot break:

Feature toggles: separate deploy from release

Big batches usually exist because a feature is not finished, and nobody wants half a feature in production. Feature toggles remove that reason. Code ships to production behind a toggle that is off. The agent can land twenty small changes over two weeks, each one deployed and tested, and the feature turns on only when it is ready. Turning it on is a config change, and so is turning it off.

Toggles also let you release slowly: first to one region, one product group, or a small sample, then wider. A two-step path works well. First a light test on a small sample that one team can run on its own. Then a formal experiment that involves the other teams. Most bad ideas die cheaply in the first step.

Toggles are also decay. Every toggle is a branch in the code. This is why the self-maintenance loop matters: once a feature is fully on, an agent removes the toggle and the dead path.

Regression tests: the contract that makes refactoring safe

Sections 1 and 2 both ask you to refactor a lot: move logic into primitives, remove dead code, merge duplicates. On a large brownfield system, refactoring is scary because nobody is sure what the old behavior was. That fear is what keeps complexity in place.

Regression tests remove the fear. If you can show that the system makes the same decisions after a refactor as before, the refactor is safe. For many systems the strongest form is a replay test: run the old and new code on the same recorded inputs and compare the outputs. Where they match, the refactor is proven. Where they differ, the difference is either a bug or an intended change, and the explainability primitive tells you which.

This is the point where the three ideas connect. Primitives (testing and evaluation, and data) make regression testing cheap. Regression testing makes self-maintenance safe. Self-maintenance keeps the code base small enough that each change stays small. And small changes keep the factory fast.

Coding is cheap. Communication and end-to-end testing are still expensive. A brownfield factory spends its effort on the expensive parts: shared primitives so teams talk less, and replay and regression tests so changes need less end-to-end testing.

How the pieces fit

Put together, the factory for a large brownfield system looks like this:

  1. A small set of shared primitives (data, testing and evaluation, explainability, knowledge base) absorbs the cross-cutting complexity, so each application is a mid-sized project again.
  2. Three streams of work (features, operational feedback, and refactoring) run side by side, and a maintenance loop keeps the code base from decaying. Agents do the chores, written rules guard the architecture at every stage, and a complexity budget keeps the numbers honest.
  3. Small, continuous changes keep each task within an agent’s context. Feature toggles let unfinished work ship safely, and regression tests make refactoring safe.

None of this is new. Abstraction, maintenance, and continuous delivery are decades old. What is new is that agents change the economics. Writing the code for a primitive, a cleanup, or a regression suite used to be the expensive part, so teams skipped it. Now it is the cheap part. The expensive parts are the ones agents cannot do alone: agreeing on interfaces across teams, and proving that a change is safe. Put your effort there.

Where to start

If you own a large brownfield system and want to try this, don’t start with the factory. Start with the properties:

  • Pick one painful, repeated thing (usually input data or test environments) and turn it into a primitive that two teams share.
  • Build one replay test for your most important decision path. It will pay for itself the first time someone refactors it.
  • Write down three architecture rules that keep getting broken, and turn them into checks that run on every change.
  • Set a size limit on changes and put everything bigger behind a toggle.

Then measure the one number that matters: how long it takes to go from an idea to a tested result. If that number is falling, the factory is working, no matter how old the code is.

Next: what is “software”?

This post treated software as a code base. That is only half of it. Software is also its runtime: the requests it receives, the dependencies it calls, the data it reads, and the environment it runs in. Much of a system’s real behavior lives there, not in the code. Two copies of the same code can behave very differently under different traffic and different dependencies.

That is why end-to-end testing for brownfield systems needs more than unit tests. It needs regression tests together with sampled production data, so the test sees the requests and dependency responses the system really gets.
