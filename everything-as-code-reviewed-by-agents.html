Everything as Code, Reviewed by Agents: Ending Fragmentation in a Federated Architecture

Federated architectures are right about ownership and wrong about discovery. Declare data, skills, agents, and code as code in the owner’s repo, let agents review every change, and keep people on the loop to write the rules.

1,700 words~7 min read2026-11-17

In short

  • Federation puts each team in charge of its own services and data. That is right for speed and ownership, but nobody can find what exists, and every team governs it differently.
  • Agents make this worse and better. Skills and agents multiply faster than services ever did, but agents can also review every change, which people never could.
  • Manage everything as code: data contracts, skills, agent specs, and code, each declared in the owner’s repo.
  • Let agents review every change against rules that people write and own, also as code. People move from reviewing each change to defining what good looks like.
  • Build the catalog from the repos, so discovery never goes stale. Federate the ownership, centralize the rules, automate the review.

The long-standing problem

Large organizations federate for good reasons. The team that runs a service knows its data best, so it should own the schema, the quality, and the access. A central team that tries to own everything becomes a bottleneck.

But federation has a cost that never goes away: fragmentation. Data is spread across hundreds of services and stores. Each team describes it in its own way, if at all. So the same questions keep coming back:

  • What exists? Is there already a dataset with order history, or should I build one?
  • Who owns it? Is the owner still on that team? Is anyone maintaining it?
  • Can I use it? How is it classified? Is it allowed for this purpose? How long can I keep it?
  • Is it any good? Is it fresh? Does it still match what the docs say?

The usual answers have each failed in their own way:

ApproachWhat happens
A central catalog, maintained by handIt goes stale. Keeping it current is nobody’s main job, so it describes last year’s systems.
A central review boardIt becomes a queue. Reviews come weeks late, so teams route around them.
Centralize the data itselfIt fights ownership. The team that knows the data no longer controls it, and the central team cannot keep up.

Agents raise the stakes

Agents make the problem bigger. Data is no longer the only thing to discover and govern. Every team now writes skills, prompts, and agents, and they multiply faster than services ever did. Two teams write the same skill without knowing it. An agent gets broad permissions because nobody reviewed its spec. A skill keeps running after the system it drives has changed.

Agents also make the problem solvable. Governance never kept up because people did the review, and people do not scale to every change in every repo. An agent can review every change, the same way every time, in minutes. That changes what is possible, if two things are true: the assets are something an agent can read, and the rules are something an agent can apply.

Both lead to the same principle.

Manage everything as code

Infrastructure as code showed the way. Declare the thing in a file, keep the file in Git, change it through code review, and let a pipeline apply it. The file is the source of truth, and everything else is generated from it.

Apply the same principle to every asset that people and agents need to find or check:

AssetDeclared asWhat the declaration holds
DataA data contract next to the code that produces the dataOwner, description, schema, classification, PII fields, retention, freshness
SkillsA skill file in the owner’s repoWhat it does, the system it drives, its evals, the permissions it needs
AgentsAn agent specIts tools, permissions, model, instructions, and owner
CodeThe code itselfOwnership, interfaces, and the tests that define its behaviour
Review rulesRule files in a governance repoWhat must be true, why, how severe, and examples

A data contract can be this small:

# datasets/order-events.yaml, in the owning team’s repo
kind: dataset
name: order-events
owner: team-orders
description: One record per change in an order’s state.
classification: confidential
pii_fields: [customer_id]
retention: 400d
schema: schemas/order-events.avsc
freshness: 15m

Managing it as code gives you a lot for free. Git already provides ownership (who can merge), history (who changed what, and when), review (every change is a pull request), and rollback. And because the declaration sits next to the code that produces the data, the two change in the same review. A schema change that forgets to update the contract shows up in the diff.

One rule makes it work: if it is not declared in a repo, it does not exist. The catalog does not accept entries typed into a web form.

Discovery: the catalog is an index, not a database

Once every asset is declared in a repo, the catalog stops being something people maintain. It becomes an index, rebuilt from the repos on every merge, like a search engine over code. It cannot go stale, because it has no state of its own. It is the pattern from Stateless Apps, Central Data: the catalog is a view, and the repos hold the data.

This matters even more for agents than for people. Before an agent writes a new skill or builds a new dataset, it can search the catalog for one that already exists. When two teams declare things that look the same, an agent can notice and suggest merging them. And a generated catalog can show signals that a hand-written page never could: when each asset last changed, whether its owner is still on the team, and whether its tests and evals still pass.

Governance: agents review, people write the rules

Every change to every asset is a code review. An agent reviews it against the organization’s rules and comments, approves, or blocks, in the owner’s repo, before the merge. The rules cover every asset type:

  • A dataset that lists PII fields must set a retention period.
  • A new dataset must not duplicate an existing one without saying why.
  • A skill must have evals before other teams can use it.
  • An agent spec must ask only for the permissions its tools need.
  • Every owner must be a team that exists, not a person who has left.

The rules are code too. Each one is a short statement in plain language, with a severity and a few examples of good and bad changes. An agent can apply a rule written this way, and a person can read it and argue with it.

# rules/data/pii-needs-retention.yaml, in the governance repo
id: pii-needs-retention
applies_to: dataset
rule: >
  A dataset that lists any PII field must set a retention
  period, and the period must not exceed what the privacy
  policy allows for its classification.
severity: blocking
mode: shadow        # shadow: comment only. enforce: block the merge.
owner: privacy-team
examples:
  bad:  examples/pii-without-retention.yaml
  good: examples/pii-with-retention.yaml

People on the loop, not in it

This changes the human job. People in the loop review each change. People on the loop do four other things:

  1. Write the rules. The security, privacy, and platform owners who used to review changes now write down what they would have checked.
  2. Handle escalations. When the agent cannot decide, it asks a person. The answer becomes a new rule or a new example, so nobody has to answer the same question twice.
  3. Watch the rules. For each rule, track how often it fires, how often owners accept its findings, and how often they override them. A rule that is mostly overridden is wrong or unclear. Fix it or retire it.
  4. Roll rules out safely. A new rule starts in shadow mode, where it comments but does not block. Once owners mostly accept its findings, switch it to enforce.

From building an AI code reviewer, this is the lesson I keep relearning: the reviewer is only as good as its rules, and the rules only get better when someone owns them and measures them.

Why this ends the fragmentation

Put together, the four pieces look like this:

  • Ownership stays federated. Data, skills, and agents live in their owners’ repos, next to the code. Nobody gives up control.
  • Description is uniform. Every asset uses one of a few declaration formats, so a dataset from one team reads like a dataset from any other.
  • Discovery is central, and generated. The catalog is rebuilt from the repos, so it is always current.
  • Governance is central, and automated. The rules are written once, centrally, and an agent applies them to every change, locally.

Federate the ownership, centralize the rules, and automate the review. Each part fixes one failure from the table above. Generated discovery fixes the stale catalog. Agent review fixes the review queue. And declarations in the owner’s repo end the fight over ownership, because the data never has to move.

How to start

  1. Pick the asset that hurts most. For most organizations, that is data. Define a minimal declaration: owner, description, classification, and schema. Add fields later.
  2. Generate the catalog from the repos. Do not import the old catalog. Ask owners to declare their assets, and treat anything undeclared as unknown.
  3. Write five rules. Start with the checks reviewers already do by hand, and run them in shadow mode.
  4. Measure, then enforce. Promote a rule when owners mostly accept its findings. Retire the ones they mostly override.
  5. Extend to skills and agents. Same pattern, new declaration formats, new rules.

Federation was always right about ownership. What it lacked was a way to describe and check what every team owns without a central team doing that work by hand. Declarations as code provide the description, agents provide the review, and people on the loop provide the judgment. That is how a federated organization finally knows what it has.
