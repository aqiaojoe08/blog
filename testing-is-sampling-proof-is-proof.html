Two Ways to Verify Software: Sample the Behavior, or Prove It

Tests are behavior samples, and the best samples come from production. When 99.99% is not enough, you need a proof, and proofs just got much cheaper.

1,900 words~8 min read2026-11-04

Two ways, not one

There are two ways to verify that software does what it should.

  1. Sample its behavior. Pick inputs, run the system, check the outputs. Unit tests, integration tests, load tests, canaries, and evals are all this. The result is statistical: the system is correct on the samples, and probably correct on inputs that look like them.
  2. Prove it. Describe the system, or a model of it, in mathematics, state the property you care about, and show the property holds for every input. Type systems, model checkers, SMT solvers, and proof assistants are all this. The result is logical: no input violates the property, within the limits of the model.

Most teams do only the first and talk about it as if it were the second. This post is about getting both right: where the best samples come from, and when it is worth paying for a proof.

Testing is sampling, not exhaustion

There is a persistent illusion that if you write enough tests, you can show a system is correct. It feels like rigor. It is not. You pick a finite set of inputs, observe the outputs, and conclude the system behaves as expected for those inputs. The rest of the behavior space is unobserved. This is not a failure of discipline. It is arithmetic.

The combinatorial wall

For a function with three independent input dimensions (say user role, request type, and environment), the test space is the product of all three. Add a fourth and it multiplies again. Real systems have dozens of dimensions. Exhaustive testing is not a goal you reach with more effort. It is a goal that does not exist.

“Just cover the edge cases” does not escape the wall either. For one string input, edge cases include empty, single character, maximum length, Unicode, null bytes, newlines, surrounding whitespace, strings that look like numbers, SQL, or HTML. That is ten categories already, and each one combines with every other dimension. Edge cases multiply like everything else.

Tests are evidence, not proof

A good suite is a stratified sample: boundary conditions, the common paths that carry most traffic, known failure modes, and adversarial inputs. Even then, a passing suite means the system is correct on the sampled behaviors. The strength of that evidence depends on three things:

  • How well the sample covers the risk surface, not how many tests there are.
  • How stable the behavior is. A flaky test is negative evidence.
  • How close the sample is to production. A test that passes in isolation and fails under real load is a gap in the sample.

This matters more now that agents can generate hundreds of tests in minutes. If an agent keeps sampling the same region of the behavior space, because that is where its training signal is dense, coverage of low-risk behavior goes up while high-risk behavior stays unsampled. The metric improves and the confidence is misplaced. 100% line coverage means every line ran once. It says nothing about the combinations.

Data-driven and ML systems make this sharper. Their behavior space is defined by a data distribution, and the test set is a sample of last year’s distribution. Production drifts, and many of these systems shape the data they later learn from. A passing eval is evidence about the old distribution, not the live one.

The third bullet above is the important one. It leads to the first meta-point.

The best samples come from production

If tests are samples, the question is no longer “do we have enough tests?” but “is our sample representative of the behavior that matters?” And there is exactly one place where the real distribution of behavior lives: production.

Every test written before launch is a guess about that distribution. A good engineer guesses well, but the guess is shaped by what the engineer imagined: the happy path, a few boundaries, the bugs they have seen before. Production does not need to imagine. It contains the combinations nobody thought of, in the proportions they actually occur. That is why so many bugs are first found in production even in well-tested systems: the pre-production sample was drawn from the wrong distribution.

So treat production as the primary source of behavior samples, and pre-production tests as the seed. There are two ways to collect them.

1. Collect blindly

Capture real requests (all of them, or a uniform or stratified slice) and replay them against new versions of the system. Shadow traffic, record-and-replay, and diffing the output of the old and new versions all fall here. You do not need to know in advance what the interesting inputs are. The traffic tells you.

  • Strength: representative by construction. The sample has the right shape, including the long tail of odd combinations.
  • Weakness: mostly redundant. Most requests look like each other, and rare dangerous inputs stay rare. You also need an oracle. Comparing against the previous version catches regressions, not bugs both versions share.
  • Cost to manage: privacy and data handling. Scrub or synthesize sensitive fields before a request becomes a test fixture.

2. Collect by feedback

Let production find the bugs, then turn each bug into a permanent sample. Every incident, customer ticket, alarm, and on-call fix contributes the exact input that broke the system, plus the expected output somebody had to work out to fix it. That input becomes a regression test, and the suite grows toward the regions where the system actually fails.

  • Strength: high signal. Each sample is known to matter, because it already hurt once, and it comes with an oracle.
  • Weakness: reactive. Someone pays for the bug before it becomes a sample.

The two work well together. Blind capture gives you the shape of normal behavior and catches regressions early. Feedback gives you the sharp edges. Over time the suite becomes a record of how the system is really used and how it really fails, not of what someone predicted before launch. This is also where agents help most: turning an incident into a minimal reproducing test, and deduplicating a million captured requests into a few hundred that cover distinct behavior, are both jobs an agent does well.

Done well, this gets you a system that is statistically correct: 99.9%, 99.99%, maybe more, on the traffic it actually sees. For most software, that is the right target. But both methods share one limit. They learn from what already happened. Some failures are not allowed to happen even once.

When 99.99% is not enough: prove it

In security, aerospace, industrial control, medical devices, and cryptography, “we will add the bug as a test after it happens” is not an acceptable plan. The first failure is the catastrophe. An authorization check that is right on 99.99% of requests is a vulnerability, because an attacker does not sample from your traffic distribution. They search for the 0.01%.

No amount of sampling closes that gap. For these properties you need the second kind of verification: state the property precisely and prove it holds for all inputs. This is what formal methods do. A proof assistant such as Lean or Coq checks a proof step by step. A model checker such as TLA+ explores every reachable state of a design. An SMT solver such as Z3 either proves a property for all inputs or produces a concrete counterexample.

The barrier just dropped

Formal methods have always been the right answer for these domains, and the wrong answer for almost everyone else, because of cost. Writing a specification took specialists. Writing the proof took more specialists, and often more time than writing the code. That cost is falling fast.

  • Agents can draft specifications and proofs. Translating code or a design into a formal model, writing lemmas, and grinding through proof obligations are tedious, mechanical, and checkable. That is the ideal job for an agent: when it is wrong, the checker says so.
  • The checker is the oracle. With generated tests, you still have to trust that the agent picked meaningful cases. With generated proofs, you only have to trust the property you stated and the checker that verified it. The agent’s output no longer needs to be trusted.
  • Tooling is closer to everyday code. Teams are now proving properties of agent harnesses in Lean (see Kiro’s post on harness properties in Lean), and SMT solvers are a library call away from most languages.

This changes formal verification from a special project into a tool you reach for when sampling is not enough. It also makes AI-driven development safer at scale: if a property is proven, it does not matter whether a person or an agent wrote the code that satisfies it.

You do not need to be in aerospace to use it

Most business systems do not need 100% correctness everywhere. But many contain a small mathematical core where an assumption, if wrong, silently breaks everything above it. There, formal methods can be a good complement to sampling, and sometimes the cheaper option, provided the problem can be abstracted into a clean mathematical model.

One example from my own area: an inventory planning model searches over order quantities and relies on its weekly net-present-value function being quasiconcave, so that a local search finds the global optimum. You could test that with thousands of sampled parameter combinations and still miss the corner where it fails. Instead, the team encoded the function and the property in Z3 and asked the solver for a counterexample. If none exists, the property holds for every input in the model, and the optimizer’s core assumption is proven, not hoped for. A few hundred lines of solver code replaced an unbounded amount of sampling.

Leslie Lamport put the progression well: writing is nature’s way of letting you know how sloppy your thinking is, and mathematics is nature’s way of letting you know how sloppy your writing is. For software, I would add one step in the middle: writing shows how sloppy your thinking is, coding shows how sloppy your writing is, and mathematics shows how sloppy your coding is.

Choosing between them

Behavior samplingFormal proof
GuaranteeStatistical: correct on observed and similar inputsLogical: correct for all inputs, within the model
Best sourceProduction traffic, blind capture plus bugs fed backA precise property and a clean mathematical model
Fails whenThe sample misses the region where the bug livesThe model or the property does not match reality
Right forMost business logic, UIs, integrations, ML systemsSecurity boundaries, safety-critical control, core algorithms and their assumptions
Agent’s roleTurn incidents into tests, deduplicate captured trafficDraft specs and proofs that a checker verifies

The two are not rivals. A proof covers only what the model captures, and models leave things out: I/O, configuration, the environment. Sampling from production checks the whole system as it really runs, with the gaps described above. A mature system uses proofs for the small core that must never fail, and production-driven sampling for everything around it.

Tests are samples, so take them from where the real distribution lives: production. Proofs are guarantees, so spend them where one failure is too many. Both just got cheaper.
