The Missing Layer Between Prose and Code: What STE, SQL, and Dogwood Teach Us About Specs

7,700 words~34 min read2026-08-07

The premise

Spec-driven development has a load-bearing assumption: that if we write requirements carefully enough, an LLM can turn them into correct code. The problem is not effort. It is that free-form natural language — even organized with EARS — cannot carry the precision production software needs. Two engineers read the same paragraph and build two different systems. Neither is wrong, because the paragraph never decided.

The way out is to treat ambiguity reduction as a four-stage pipeline, where each stage compresses the ambiguity of the one before it:

Free-form natural language → Controlled language → Executable tests → Verified implementation

StageWhat it isWhat it removes
1Free-form proseNothing — the baseline
2Controlled languageInterpretation ambiguity, unstated constraints
3Executable testsAmbiguity about intended behaviour — the test is the answer
4Verified implementationDrift between spec and code

Most teams jump from 1 straight to unverified implementation (vibe it, hope), or from 1 to 3 (write tests, let the AI code). Stage 2 is the one everybody skips, and it is the only stage that fixes the spec itself rather than catching a bad spec's consequences downstream.

This post is about stage 2, through three examples that are unusually instructive because they come from three completely different worlds: aerospace maintenance manuals, relational data query languages, and agent authorization.

Two problems, one fix: the DSL

Strip spec-driven development down and there are exactly two things that can go wrong between a human's intent and a running system. They are usually lumped together as "the AI got it wrong," but they are different failures, sitting at different points in the flow — and the useful observation is that a single move closes both of them: introducing a DSL as the intermediate.

ProblemWhere it livesHow the DSL closes it
1 · Ambiguity of natural language — prose cannot carry the precision a requirement or design actually needs, so two readers build two systemsIn the spec, before any code existsThe DSL's closed vocabulary and single parse make imprecision impossible to write down
2 · LLM uncertainty — the same input, handed to a model, translates into different code on different runsIn the realization, spec → behaviourThe DSL is a machine-processable artifact, so a deterministic engine — a compiler, an interpreter, or a fixed engine reading it as config — turns it into behaviour the same way every time

It is one fix, not two, because the second property is a consequence of the first. The DSL solves problem 1 by construction: its precision and conciseness are exactly the ambiguity of prose, removed. You cannot type a Dogwood rate limit without deciding rolling-vs-calendar, per-principal-vs-global, request-vs-response — the notation has slots, and empty slots are errors. That is problem 1, closed at the source.

And because the artifact is now a DSL rather than prose, problem 2 is closed for free — as long as you resist re-introducing a model at the wrong step. The trap: if you ask an LLM to interpret the DSL afresh on every run, you have merely moved the non-determinism one step downstream, and the same input can still produce different behaviour. The escape is that a DSL, unlike prose, is machine-processable, so a deterministic engine can carry it to behaviour — and "engine" is deliberately broad. The DSL might be compiled to a general-purpose language and then built; interpreted on the fly by a fixed evaluator (Dogwood ships exactly this — a reference interpreter); or not turned into code at all, existing only as configuration that a generic engine reads, where the config carries the variable parts and the engine already holds the domain invariants. What matters is not which of these you pick but that the step is deterministic: the same DSL yields the same behaviour every time. Non-determinism is then confined to a single step (intent → DSL), which a human reviews once; everything after the reviewed artifact is a pure function, repeatable and auditable.

Config, in other words, is not the opposite of a DSL — it is one of the forms a DSL can take. A YAML file is a DSL when it has a closed vocabulary, a schema that rejects the malformed, and a fixed engine that gives it meaning. AutoSDE is the vivid case: it expresses inheritance, composition, and public/private scope — semantics we think of as belonging to a general-purpose language — but does so as YAML, with a generic engine supplying the machinery and the config supplying only what varies. The GPL-grade power is real; the surface is declarative data.

So the two problems have one answer with two payoffs. Until we have the next generation of general-purpose language that carries this precision natively, a DSL is the pragmatic way to buy both at once: the notation supplies the precision prose lacks (problem 1), and being a machine-processable notation at all is what lets a deterministic engine — compiler, interpreter, or config runtime, not another LLM guess — carry it to behaviour (problem 2). The rest of this post is the long form of that argument — what the notation should look like, who should own it, and where the deterministic boundary belongs.

Example 1: Simplified Technical English — a controlled natural language

ASD-STE100 Simplified Technical English is what you get when an industry constrains prose itself. Born in aerospace (originally AECMA Simplified English, 1986) for maintenance manuals read by non-native-English technicians under time pressure, STE is not a programming language — it is English with the ambiguity legislated out:

  • A closed dictionary of roughly 900 approved words, each with one approved meaning and one part of speech. follow means "come after" — if you mean "obey", the approved word is obey.
  • Roughly 60 writing rules: active voice, one instruction per sentence, sentence-length caps (about 20 words for procedures, 25 for description), no ambiguous participles, no omitted articles.
  • Technical names and verbs outside the core dictionary are allowed but must be declared for the project.

The effect, illustrated:

Unconstrained: "Ensure that the retaining bolt is not overtightened, as this may result in damage to the housing."

STE-style: "Do not tighten the retaining bolt to more than 12 Nm. More torque than 12 Nm damages the housing."

The rewrite is not shorter, it is decided. "Overtightened" had no referent; the rewrite forced a number to exist. That is the whole game at stage 2: a controlled language's real output is not cleaner text but a list of decisions someone had to make before they could write the sentence at all. STE is the proof of existence — you do not need to leave natural language to leave ambiguity, only to adopt a closed vocabulary and a single parse.

Example 2: SQL — the DSL everyone already accepted

SQL is the most widely deployed stage-2 language in the industry, and nobody thinks of it as one.

Take a business request: "show me active customers with high spending." Three questions hide in eight words — what is active, what is high, over what window? Prose lets you ship that sentence into a backlog. SQL does not:

SELECT customer_id, SUM(order_total) AS spend_12mo
FROM   orders
WHERE  order_date >= CURRENT_DATE - INTERVAL '365 days'
GROUP  BY customer_id
HAVING SUM(order_total) > 1000
   AND MAX(last_login_at) >= CURRENT_DATE - INTERVAL '30 days';

You cannot type this without answering all three questions: SELECT / FROM / WHERE / GROUP BY / HAVING is a set of slots, and empty slots are syntax errors or visible omissions. Prose has no slots — that is exactly its problem.

SQL also shows the property that makes stage 2 economically viable: it is readable by the person who asked the question. An analyst who cannot write Java can read the query and say "no, 30 days should be 90." That review loop is the value — and executable tests (stage 3) mostly lose it, since a JUnit assertion is not something a business stakeholder audits.

Example 3: Dogwood — a controlled language for agent behaviour

Dogwood (AWS, open source, Apache 2.0) is the newest and sharpest example, because it appeared where prose specs were failing hardest: telling an AI agent what it may not do.

Dogwood extends Cedar. Where Cedar judges this request alone, Dogwood adds temporal conditions grounded in Metric First-Order Temporal Logic, so policies reason over the sequence of an agent's tool calls. Every valid Cedar policy stays valid; deny-by-default and forbid-overrides-permit are unchanged. Policies evaluate over a trace of events — each a tool-call request or response — and the action schema can be generated from the agent's MCP tool manifest.

Here is a rule an ops team would otherwise write in a wiki page:

forbid ( principal, action == AgentCore::Action::"Transfer", resource )
when temporal {
    sum_within(a, 1h, AgentCore::Action::"Transfer"::request{ input.amount: a }) > 5000
};

Four lines: the agent may not move more than $5,000 per rolling hour. The prose version — "the agent shouldn't transfer more than $5k an hour" — is 11 words and leaves at least four questions open. Rolling window or calendar hour? Per principal or global? Counted at request or at settlement? Does a denied attempt count?

The third question is not academic. Swap one word, request → response, and the policy becomes wrong:

forbid ( principal, action == AgentCore::Action::"Transfer", resource )
when temporal {
    sum_within(a, 1h, AgentCore::Action::"Transfer"::response{ input.amount: a }) > 5000
};

Now only settled transfers count. An agent — which, unlike a human, happily fires calls in parallel — can put three $2,000 transfers in flight before any resolves: the request-based policy denies the third at $6,000 in flight, the response-based one allows it. $6,000 leaves the building under a $5,000 policy. Prose cannot express that distinction, so prose rate limits are silently underspecified and the ambiguity gets resolved at 3am by whoever implements the counter. Dogwood cannot avoid expressing it: you must type request or response.

The operator vocabulary is deliberately tiny — formerly (did it happen), count_within (how many), count_distinct_within (how many different), sum_within (how much total), bind (compare against an aggregate) — and all but formerly are standard-library macros over a small MFOTL core. Same instinct as STE's 900-word dictionary: a closed vocabulary, one meaning per term. Enforcement is at the tool-call boundary — AgentCore Policy in Amazon Bedrock AgentCore evaluates each call — and the open source release ships a parser, validator, and reference interpreter.

Notice too how Dogwood explains itself: alongside each policy the docs give a trace, a worked sequence of events with a verdict per request. For a rule requiring an approval within the last hour before a sale:

@0     SellShares::request   { stock: "AMZN", shares: 100 }                 -> DENY
@1700  ApproveSale::response { stock: "AMZN", shares: 100, approved: true }
@1800  SellShares::request   { stock: "AMZN", shares: 100 }                 -> ALLOW
@7200  SellShares::request   { stock: "AMZN", shares: 100 }                 -> DENY

Even the authors of a formal language reach for examples — and those examples are exactly the shape a test case takes: stage 3 on top of stage 2, not instead of it. Note the last request arriving before the previous one's response — the parallel interleaving the request/response distinction turns on.

"But DSLs are hard for humans to write"

This is the standard objection, and it was correct for thirty years. It is now the wrong frame.

The objection assumes the same person must both author and read the notation. Drop that assumption and a DSL's cost structure splits in two, along a seam that has always been there:

Hard for humans?Hard for AI?
Writing the DSLYes — you must learn the grammar, the operator set, the corner casesNo — closed vocabulary, small grammar, deterministic semantics, and a validator that says wrong out loud
Reading the DSLNo — that is what it was designed forn/a
Translating intent → DSLThe expensive partThis is the machine's best trick

So the workflow inverts. The human supplies intent in whatever form intent naturally arrives — "the agent shouldn't move more than $5k an hour" — and the model emits the notation:

forbid ( principal, action == AgentCore::Action::"Transfer", resource )
when temporal {
    sum_within(a, 1h, AgentCore::Action::"Transfer"::request{ input.amount: a }) > 5000
};

Then the human does the thing humans are good at: reads four lines and checks them. "Rolling hour, per principal, counted at request — yes, that's what I meant." Total time: seconds. No MFOTL required.

Notice what happened in that loop. The ambiguity in the original sentence did not vanish silently — it got resolved into something visible. The model had to type request or response; there is no third option, no way to stay vague. Every decision the prose left open now appears on the page where a reviewer can accept or reject it. That is the whole value of stage 2, and it survives the human never having learned the language.

Three reasons a DSL is specifically a good compilation target for an LLM, more so than general-purpose code:

  • Small, closed grammar. Dogwood's operator vocabulary is five things. Fewer ways to be wrong.
  • A validator in the loop. Parser and type-checker reject malformed output immediately — a hard, cheap, non-negotiable signal, unlike a natural-language spec where nothing ever fails to parse. Dogwood ships a parser, validator, and reference interpreter; Cedar adds automated reasoning on top.
  • Short output. Non-determinism compounds with length. A four-line policy has far less room to drift than the four hundred lines of enforcement code you would otherwise have asked for — and that is the alternative. The choice was never "write Dogwood by hand or write English." It was "review four lines of Dogwood or review four hundred lines of hand-rolled rate limiter."

The asymmetry is the design goal, not a happy accident. A good stage-2 language is easy to read, easy to validate, and therefore easy to generate. Optimize a notation for human authoring ergonomics and you tend to add flexibility, shorthand, and multiple ways to say the same thing — which is exactly the ambiguity you were trying to remove. Optimizing for reading and checking pushes the other way. The DSL is not the artifact you write; it is the artifact you agree on.

One caveat follows directly, and it matters more than it sounds: this loop only works if the human actually reads the output. Natural language is redundant, and redundancy is error-detecting — if a sentence contradicts itself, a reader notices. A four-line policy has no redundancy at all, so a one-word error is invisible on review and catastrophic in production. Dense notation moves the failure mode from misunderstood to silently wrong. AI-generated DSL that nobody reviews is therefore worse than prose, because it looks authoritative and has nothing to trip an error against. The review step is not optional overhead — it is where the specification actually gets decided. And it is worth pairing with stage 3: have the model emit worked traces alongside the policy, so you review behaviour and not just syntax.

Should every team define its own DSL?

If generating DSL is now cheap, the next question arrives immediately: does each team roll its own?

You can. It is not wrong, and for a genuinely local problem it is fine. But it scales badly for a reason that has nothing to do with effort: a private notation loses the property that made stage 2 worth doing. The value of a controlled language is shared, unambiguous meaning. A dialect only your team parses is precise internally and opaque at every boundary — and boundaries are exactly where specs fail. Two teams each with a crisp private DSL for "order" will still ship an integration bug, because nothing forced their two orders to be the same thing.

Per-team notations also fail to amortize. Every DSL needs a grammar, a validator, an interpreter, editor support, and a body of worked examples. Multiply that by team count and you have spent a platform budget to produce mutually unintelligible artifacts.

The layering that actually works

The fix is not one universal language either. A DSL is only precise inside its domain — SQL says nothing about why a customer matters, Dogwood nothing about whether the agent is useful — and that narrow scope is the source of the precision, so a language broad enough to cover everything would be precise about nothing. The fix is to separate the layers:

LayerWhat it fixesWho owns itChanges
Domain vocabulary — the nouns, identifiers, and events of a verticalWhat things are; shared meaning across teamsThe vertical (ideally anchored on an external standard)Rarely
DSL — operators, grammar, evaluation semantics over those nounsHow to say things about them, checkablyPlatform / language owner, reused across verticalsSlowly
Policies / specs / queries — actual statementsThe specific decisionThe teamConstantly

Teams should be authoring the third row, not the first two. When a team feels the urge to invent a DSL, what they usually actually need is a profile: the shared vocabulary, restricted to their subset, with their own values plugged in.

Dogwood is a clean demonstration of this discipline. It invents remarkably little. Its noun layer — the action schema — is generated from the agent's MCP tool manifest, so the vocabulary of actions comes from an existing artifact rather than a new registry. Its authorization semantics are inherited wholesale from Cedar, deliberately, so that every valid Cedar policy stays valid. Its temporal semantics are borrowed from Metric First-Order Temporal Logic, decades-old and studied. And its five operators are macros over a small MFOTL core rather than primitives. The genuinely new contribution is a thin layer of temporal glue. That ratio — mostly anchored, slightly novel — is the template, and it is why the language arrived with a parser, validator, and interpreter instead of a manifesto.

The standards opportunity

This is where the real leverage sits, and it is larger than it looks. Most verticals already have a standardized vocabulary written by a committee that spent years arguing about exactly the ambiguities your team is about to rediscover. Anchoring a DSL on one of those buys you a noun layer for free, plus interoperability you did not have to negotiate.

The instinct to look at IEEE is right, but it is worth being accurate about who owns what, because the address differs sharply by vertical:

VerticalWhere the vocabulary already lives
Security / threatMITRE CVE, CWE, CAPEC, ATT&CK; OASIS STIX (threat intel), OpenC2 (defensive actuation); NIST SCAP and OSCAL — a machine-readable control/assessment language, one of the closest existing things to a stage-2 security DSL
Authorization / policyCedar, OASIS XACML, W3C ODRL (rights and usage), Rego/OPA
Software supply chainSPDX (ISO/IEC 5962), CycloneDX (ECMA-424), in-toto attestations, SLSA levels
Physical supply chainGS1 — GTIN identifiers and EPCIS, an event vocabulary for what/where/when/why, also standardized via ISO/IEC
Pricing / financial messagingISO 20022, FIX, FpML — strong on message vocabulary, notably weak on pricing rule semantics
Requirements engineering itselfISO/IEC/IEEE 29148 (successor to IEEE 830) — this is where IEEE genuinely owns the ground
Event tracesIEEE 1849 XES — an event-log standard from process mining, and a plausible anchor for agent-trace vocabularies of the kind Dogwood evaluates over

(Fit varies; verify the specific edition before committing to one.)

Now the honest part, which is also where the opportunity actually is. Most of these standards give you nouns, not semantics. They are largely prose documents and schemas — they standardize what a term means to a human reader and what a message looks like on the wire. Very few define machine-checkable rules over their own vocabulary. You can validate that a STIX bundle is well-formed; you cannot write "no analyst may pivot to an external host after touching this indicator" in STIX and have something enforce it.

That gap is the whole prize: a stage-2 rule language layered over an existing standard vocabulary. Cedar/Dogwood over an MCP tool manifest is one instance of the pattern. OSCAL is another domain that got partway there. The same move is unmade in most verticals — supply chain, pricing, data handling — and it is unmade not because it is technically hard but because it needs someone to pick the vocabulary and write the ten operators that matter for that domain.

Three caveats before anyone drafts a charter:

  • Standards lag and standards bloat. Committee vocabularies are often superset-by-negotiation, carrying terms no one uses because some member needed them. Anchoring means profiling a subset, not adopting wholesale.
  • Anchor on identifiers first. Even if you take nothing else, using the standard's identifiers (CVE IDs, GTINs, SPDX license expressions) buys most of the interoperability at almost no cost.
  • Pick the anchor before the operators. The nouns are the expensive, political, long-lived decision. Operators are comparatively easy — Dogwood needed five.

The short answer to the original question: teams should not own languages, verticals should own vocabularies, and everyone should write policies. A team inventing a DSL is usually a symptom that its vertical never agreed on nouns.

Language-Oriented Programming, revived

Everything above has a name, and it is thirty years old.

Language-Oriented Programming (LOP) — coined by Martin Ward in 1994 — inverts the usual order of work. Instead of solving a problem directly in a general-purpose language, you first design a language that expresses the problem domain, then state the solution in that language, and separately build the machinery that executes it. The program becomes a description of what, and the language implementation carries the how. Ward's argument was that the resulting solution is shorter, closer to the domain, and easier to change, because domain changes touch domain-level statements rather than diffuse code.

Its close relative is meta-programming: programs that write or manipulate programs. Lisp macros, Template Haskell, Rust proc-macros, C++ templates, annotation processors, code generation, and multi-stage programming (MetaOCaml, Lightweight Modular Staging) all live here. The relationship is that meta-programming is usually how you implement a language inside another one — internal DSLs are a macro system away, external DSLs need a parser.

The lineage is a graveyard of good ideas:

  • Ward's LOP paper (1994) — the naming.
  • Intentional Programming — Charles Simonyi's bet that programs should be stored as intent and projected into notations; Intentional Software ran for ~15 years, acquired by Microsoft in 2017.
  • Model-Driven Architecture / UML (OMG, early 2000s) — the most heavily marketed attempt, and the one that discredited the field for a generation.
  • Language workbenches — Fowler's 2005 essay called them "the killer app for DSLs." JetBrains MPS and Xtext are the surviving serious implementations.
  • Racket — the one unambiguous success. #lang makes new languages a first-class module concern, and the Racket Manifesto argues LOP explicitly.

And yet almost nobody does LOP. Worth being precise about why, because the reasons are not all the same and AI only touches some of them:

  1. Tooling cost. A notation is not a grammar. It is a grammar plus parser, type checker, formatter, LSP server, syntax highlighting, debugger, error messages, and documentation. Most of the cost was never the language design — it was the surrounding apparatus.
  2. Language design is a specialist skill. Few teams have someone who has designed a grammar, and a badly designed notation is worse than no notation.
  3. The DSL tax on humans. Every new language is an onboarding cost, a bus-factor risk, and a hiring problem. Ten team-local DSLs mean nobody can read anyone's code.
  4. Debugging leaks through the abstraction. Errors surface in generated artifacts rather than in the source notation. MDA's round-trip problem — regenerate and lose hand edits — was fatal.
  5. No ecosystem. No libraries, no Stack Overflow, no examples.

What AI actually changes

Reasons 1 and 2 are labor, and they are exactly the kind of labor models are good at: grammars (ANTLR, tree-sitter), recursive-descent parsers, LSP scaffolding, formatters, test corpora, reference docs. Building an external DSL used to be a quarter of platform work; it is now closer to a week. Reason 3 — the human learning cost — is the one dissolved by the asymmetry argument earlier in this post: if the model authors and the human only reads and reviews, the onboarding tax mostly evaporates.

But the cheaper-tooling story is the least interesting half. Two things are genuinely new, not just cheaper:

Grammars became generation constraints. This did not exist for classical LOP. With grammar-constrained decoding — GBNF, JSON-schema-mode, structured outputs, outlines-style samplers — a formal grammar can be applied at token-sampling time so the model is incapable of emitting a syntactically invalid program. A parser used to be something that rejected bad input after the fact. It is now something that prevents bad output from being generated. That converts "the model might hallucinate an operator that does not exist" from a validation problem into an impossibility. Combine that with a type checker for semantic errors and a validator-in-the-loop repair cycle, and a narrow notation becomes a more reliable target than general-purpose code, not a less reliable one.

The bottleneck moved from writing to reviewing. When generation was expensive, expressive power was the thing to optimize — hence Turing-complete general-purpose languages. When generation is nearly free and review is the constraint, the thing to optimize is how quickly a human can confirm that an artifact says what they meant. That reverses the traditional case for and against DSLs. A narrow notation's smallness stops being a limitation and becomes its central feature: four lines of Dogwood reviewed in seconds versus four hundred lines of hand-rolled rate limiter reviewed in an afternoon. LOP's value proposition shifts from productivity to verifiability, and verifiability is precisely what the AI era is short of.

The counter-asymmetry, stated honestly

There is a real force pushing the other way, and enthusiasts skip it: models are weakest exactly where a language is newest. LLM fluency tracks training corpus size. A brand-new DSL has a corpus of zero, so the naive move — invent a notation, ask the model to write it — produces confident nonsense that borrows syntax from whatever the grammar resembles.

This is not fatal, but it dictates design choices:

  • Anchor the syntax on something the model already knows. Dogwood's compatibility with Cedar is a correctness decision and also, incidentally, a generatability decision — the model has seen Cedar. Looking like SQL, JSON, or C-family expression syntax buys transfer for free. A notation with novel syntax pays for its novelty in generation quality.
  • Ship the grammar and examples as context. In-context learning substitutes for training data surprisingly well when the grammar is small. This is another argument for small: the whole language definition fits in a prompt.
  • Make the validator's errors good. Error messages are now a machine-facing interface, consumed in a repair loop. "Unexpected token" wastes a turn; "unknown operator count_since; did you mean count_within?" fixes it in one.
  • Invest in the canonical example corpus, not the tutorial. Worked examples are dual-purpose — human documentation and few-shot material. Dogwood's traces do both jobs.

Design principles invert

If a notation's primary author is a model and its primary consumer is a reviewer, the ergonomics you optimize for change sign:

Classical DSL design (human authors)AI-era design (model authors, human reviews)
Terse — minimize typingExplicit — typing is free, so spell it out
Symbols and operatorsKeywords — readable aloud, unambiguous in diffs
Shorthand, sensible defaults, implicit contextOne canonical form — no two ways to say the same thing
Flexible syntax to suit tasteCanonical formatting — so diffs are stable and reviewable
Inference to reduce annotationRedundancy where it aids review — restoring some error-detection

That last row is the interesting one, and it answers the redundancy problem raised earlier. Natural language's redundancy is what lets a reader notice a contradiction; maximally terse notation removes it. When typing cost drops to zero, you can afford to buy some of it back — deliberately, at the points a reviewer needs a second signal.

Where to keep the model out

One boundary matters. The model should be the compiler at authoring time, not the interpreter at runtime.

There is a temptation, now that models can read anything, to skip the language implementation entirely: keep the intent in prose and have the model interpret it per request. That is stage 1 wearing a costume. It reintroduces non-determinism into semantics — the same rule evaluated twice can decide differently — and it destroys every property that made the artifact worth having: no diff, no analysis, no reproducibility, no audit.

The staging that works, familiar from partial evaluation: intent → (model, once, reviewed) → DSL artifact → (deterministic interpreter, always) → decision. Non-determinism is confined to a step whose output a human signs off on. Everything downstream is exact and repeatable. Dogwood's information providers show the one disciplined exception: a learned model can be consulted from inside the deterministic shell, at a named, sandboxed, bounded point — a classifier answering one question the policy asks it, not a model deciding the whole matter.

So: revival, with a condition

Yes — and it is already happening under other names. The modern typed-config languages (CUE, Dhall, Nickel, Starlark), the policy languages (Cedar, Dogwood, Rego), tree-sitter grammars proliferating across tooling, and the notations built for orchestrating models (DSPy's "programming, not prompting" stance, LMQL, Guidance) are all LOP in practice, whether or not anyone cites Ward.

The condition is the one from the previous section: cheap languages are not automatically good languages, and cheapness makes proliferation the default failure mode. If every team can generate a notation in a week, most teams will, and the result is the mutually unintelligible dialect sprawl that killed LOP's reputation the first time — now at higher velocity. What makes this round survive is exactly the layering: verticals own the vocabulary, platforms own the notation, teams write statements. AI removes the cost of building a language. It does not remove the cost of having many languages, and that was always the harder bill.

The low-resource language problem

This is the binding constraint, so it deserves its own treatment. Models are fluent in Python, Java, and TypeScript because those have effectively unbounded public corpora. A proprietary in-house notation — a pricing rule language, an internal rules engine, a bespoke expression language — has a public corpus of zero. The model does not decline to answer. It produces syntactically plausible output by analogy to whatever the notation superficially resembles, with invented operators and misapplied semantics. Confident, wrong, and reviewable only by someone who already knows the language.

Borrowing the term from NLP, these are low-resource languages, and the category is bigger than people assume: AMPL, GAMS, MiniZinc, Mosel, TLA+, SystemVerilog assertions, Dhall, Nickel, CUE, Cedar, Dogwood, and every internal DSL ever built. The failure is not a model deficiency to wait out. Public corpus size for a proprietary language stays at zero permanently.

There are two routes out. They are not rivals — they answer different questions.

Route A: make the model learn the notation

A ladder, cheapest first. Most teams stop far too early on it.

  1. Put the whole language in context. Grammar, operator cheat sheet, ten worked examples. For a language with five operators this is a few thousand tokens, and in-context learning substitutes for training data remarkably well at this size. This is why "keep the notation small" pays twice — once in review cost, once in generatability. A language that fits in a prompt is a language the model can learn per-call.
  2. Make that context durable. Commit it as agent-facing documentation — AGENTS.md, CLAUDE.md, an llms.txt. Language docs are now a machine-facing interface, not just onboarding material.
  3. Retrieve from your own corpus. This is the most underrated item here. An organization with ten thousand existing artifacts in its internal DSL owns a private corpus that no public model has, and few teams wire it up. Retrieving the twenty most similar existing policies as few-shot examples routinely outperforms any amount of prose documentation, because it teaches idiom and house conventions alongside syntax.
  4. Constrain generation with the grammar. As above — sampling-time grammar constraints make syntactic errors impossible rather than merely detectable.
  5. Close the repair loop on the validator. Parser and type-checker errors become a reward signal in an agentic loop. This is cheap and effective, and it makes error-message quality a first-class investment: unknown operator 'count_since'; did you mean 'count_within'? converges in one turn where unexpected token burns several.
  6. Check semantics, not just syntax. Have the model emit worked traces alongside the artifact and run them. Syntactic validity is the easy half; a policy can parse cleanly and still count response where you meant request.
  7. Back-translate for review. Have a second, independent pass paraphrase the generated artifact into plain language, then compare that to the original intent. When review is the bottleneck, a round-trip catches semantic drift far faster than reading notation directly — and it lets someone who does not know the language review it.
  8. Fine-tune only if 1–7 are exhausted. And note you can manufacture the corpus: sample random ASTs from the grammar, render them to surface syntax, and have a model write natural-language descriptions for each. Grammar-driven synthetic corpora are real and effective. The costs are staleness — every language revision invalidates the tune — and losing the ability to swap models freely.

Steps 1–3 and 5 cover most of the gap for most languages, and none of them require training anything.

Route B: build the DSL as a library in a host language

This is the right default for most teams, and it is Fowler's internal (embedded) DSL versus external DSL distinction. Choosing internal buys a great deal:

  • The model's host-language fluency transfers immediately. Method chaining in Python is Python. The corpus problem largely disappears.
  • You inherit the entire toolchain — type checker, LSP, autocomplete, debugger, test framework, package manager, formatter. That was reason #1 on the list of why LOP failed, and it evaporates.
  • A typed host gives you a validator for free. In TypeScript or Scala, malformed constructions fail to compile. Route A had to build that; Route B is handed it.
  • Autocomplete-driven discovery means the vocabulary is browsable rather than memorized.

But there is a condition, and it is the whole ballgame.

The condition: deep embedding, not shallow

Recall why an external notation was attractive in the first place — it is data, and data is analyzable. Not Turing-complete, so a machine can decide things about it, diff it, aggregate it, prove properties of it. If you embed the DSL as a library that directly executes host-language code, you regain fluency and forfeit exactly that property. Now arbitrary host code is interleaved with domain statements, and the artifact is no longer analyzable — only runnable.

The FP vocabulary for this is precise:

  • Shallow embedding — library functions compute the result directly. Easy, fluent, opaque. Nothing to inspect.
  • Deep embedding — library functions build an inspectable AST, which a separate stage analyzes, optimizes, validates, and executes.

Deep embedding is the answer. It gets Route B's fluency without surrendering the analyzability that motivated stage 2. The pattern is everywhere once you look for it:

CDK: the pattern already won this argument

The CDK row deserves expanding, because it is not a thought experiment. It is the same choice, made at scale, with the outcome already known.

Infrastructure-as-code started at stage 2 in its purest form: CloudFormation and Terraform HCL, declarative artifacts, analyzable, diffable, no control flow. Textbook logic-as-config. And then practitioners hit the wall — no abstraction, no reuse, no types, copy-paste across environments, and templating layered on top to compensate — the failure mode where a config format slowly grows conditionals, loops, and interpolation until it is a Turing-complete language with YAML syntax and no debugger. Loops and conditionals arrived in YAML, and YAML was not built to hold them.

CDK's answer was Route B: author in TypeScript, Python, Java, or Go — get loops, functions, types, unit tests, an LSP, a package manager, and real abstraction — then synthesize CloudFormation. And it won on adoption against the raw YAML it compiles to, which is the interesting part. The declarative artifact did not go away; it stopped being the thing humans write. CDK for Terraform and Pulumi made the same bet independently, which is a strong signal it is the structural answer rather than a local preference.

Three things CDK demonstrates that matter directly to the corpus problem:

  • The authoring surface is high-resource, and the model benefits. A model writes CDK TypeScript well, because it is TypeScript. Ask it for raw CloudFormation and quality drops — YAML with implicit intrinsic-function semantics is a lower-resource target with worse error feedback. The host language carried its fluency across.
  • The contract survived. cdk synth emits a template you can review, cdk diff shows what will actually change, and — the load-bearing part — policy tools operate on the synthesized output, not the source program. cfn-guard, cfn-lint, CloudFormation Guard rules, and IAM Access Analyzer all read the artifact. A security reviewer never reads the TypeScript. That is deep embedding working as designed: the construct tree is an inspectable AST, synthesis is the analysis stage, and the template is the reviewable contract.
  • It confirms both of the honest costs. CDK's known complaints are exactly the two predicted above. Non-programmer readability is gone — you cannot hand a CDK app to someone who does not write code, which is why cdk diff in code review is not optional but load-bearing. And host-language semantics leak: a for loop over a list that changes length silently renames logical IDs and replaces resources. The domain never had that failure mode; the host language brought it.

So the general-purpose language is the construction layer, and the declarative output is the contract. CDK is the existence proof that this composition holds under production load — and the reason to treat the synthesized artifact as a first-class reviewable output rather than a build intermediate. The moment teams stop reading cdk diff, they have Route B's fluency with none of stage 2's guarantees.

That is the synthesis of the two routes, and it resolves the tension cleanly:

Author in a high-resource host language. Emit a low-resource declarative artifact. Analyze, review, and execute the artifact.

The model works where it is strongest. The reviewer and the verifier work on something exact and small. Nobody has to make an LLM fluent in a language with no corpus, because the notation is a compilation target, not an authoring surface.

The honest costs of Route B

Three, and they are the reason external notations do not simply disappear:

  1. The escape hatch destroys analyzability. If the host language can inject arbitrary logic — a lambda into a filter, a runtime callback — the AST contains an opaque node and analysis stops there. LINQ's long-standing failure mode is exactly this: an expression that compiles fine and then throws "could not be translated" at runtime, because the boundary between what the DSL can express and what the host can express is invisible in the source. Deep embeddings must police that border explicitly, and doing so is unglamorous work.
  2. You lose non-programmer readability. A security reviewer can read a synthesized CloudFormation template; reading the CDK app that produced it requires programming skill. That property — the requester being able to audit the artifact themselves, the thing SQL is prized for — is exactly what Route B trades away, recovered only if the synthesized artifact is treated as a first-class reviewable output rather than a build intermediate.
  3. Host-language semantics leak in. Python's numeric behaviour, evaluation order, mutability, and exceptions all become part of your domain semantics whether you intended it or not. Formal claims get harder, not easier.

Choosing

SituationRoute
Artifacts must cross team, language, or org boundaries; need audit, formal analysis, or non-programmer reviewExternal notation — pay the corpus cost, mitigate by anchoring
Used by engineers inside one stack; speed matters; analyzability is a nice-to-haveInternal DSL, shallow — cheapest thing that works
Both: engineers author, but the result must be reviewed, diffed, or verifiedInternal DSL, deep embedding, external artifact as the contract — the CDK pattern, and the right default

And if you do build an external notation, the corpus problem is a design input, not an afterthought. Ranked by how much model fluency the surface syntax inherits for free:

  1. Embedded in a host language — maximal transfer.
  2. A dialect of something high-resource — SQL-like, C-family expressions. Cedar and Dogwood sit here, which is part of why Dogwood's Cedar compatibility is a generatability decision as much as a migration one.
  3. JSON or YAML with a published schema — strong fluency, weak human readability.
  4. Novel syntax — full price, paid forever.

The principle underneath all of it: the corpus is now a design constraint on language design, alongside expressiveness and readability. Classical LOP never had to think about this. Any notation designed today that ignores it is choosing to be written badly.

What this means in practice

The pipeline argument is not "adopt formal methods." It is that ambiguity has to be trapped somewhere, and every stage you skip pushes the trapping later, where it costs more.

  • Stage 1 → 2 is the highest-leverage move most teams have not made. Ask: for the requirements we argue about most, does a controlled notation already exist? Often yes — OpenAPI, Smithy, Gherkin, SQL, Cedar/Dogwood, a state machine. Using it converts an argument into a diff.
  • Stage 2 does not need to be a new language. STE proves a closed vocabulary and a style guide over plain English gets much of the benefit. That is a week of work, not a platform bet.
  • Stop screening stage-2 languages on authoring difficulty. "Nobody on the team knows Cedar" is no longer a reason to skip a notation. Screen on the two things that still matter: can a reviewer read it, and is there a validator? Let the model write the first draft.
  • Resist the per-team DSL; find the vertical's vocabulary instead. Before designing a notation, spend a day asking whether your domain already has a standardized noun set — SPDX, EPCIS, STIX, OSCAL, ISO 20022, XES. Anchor on it, profile a subset, add the handful of operators your domain needs. A team-local dialect is precise internally and opaque at exactly the boundaries where specs fail.
  • Keep stage 3 even when stage 2 is formal. Dense specs need worked examples, because they have no redundancy to catch typos. Ask the model for the trace alongside the policy.
  • Treat stage-2 artifacts as config, and give config code-grade rigor. The upside of logic-as-data is that it ships without a rebuild; the risk is that config paths skip review, CI, canary, and rollback. Version it, review it, test it against traces, roll it out gradually. And guard the notation itself — the discipline is what you refuse to add, because a config language that grows conditionals and loops becomes an untestable programming language with YAML syntax.
  • Match stage 4 to the stakes. The economic rule: pick the verification level where the cost of writing the spec is below the cost of a wrong answer. Delta gates and property tests for CRUD; SMT and proof assistants for security- and safety-critical paths.
  • Treat the training corpus as a design constraint on notation design. A proprietary DSL has a public corpus of zero, permanently, and models fail on it confidently rather than visibly. Before inventing syntax, prefer the CDK pattern: author in a high-resource host language, deep-embed so the library builds an inspectable AST, and synthesize a declarative artifact as the reviewable contract. If you must build an external notation, anchor its syntax on something high-resource, keep it small enough to fit in a prompt, and wire up retrieval over your own existing artifacts — that private corpus usually beats any documentation you could write.
  • If you do build a notation, design it for a machine author and a human reviewer. Explicit over terse, keywords over symbols, one canonical form, canonical formatting, syntax anchored on something the model has already seen. Ship the grammar as a generation constraint, invest in error messages as a machine-facing repair interface, and keep the model at authoring time only — never as the runtime interpreter.
  • Watch the spec-checking frontier. SMT-based requirements analysis — tooling that detects conditional inconsistencies, incompleteness, and redundancy in a requirement set before any code exists — points at the capability none of these three languages fully have yet: a machine that tells you your specification is broken before any code exists. Cedar's automated reasoning is the same idea in the policy domain. When that lands for temporal policies, stage 2 stops being a discipline and becomes a compiler error.

The one-line version: an LLM will happily bridge an ambiguous spec, and it will bridge it differently every time. Controlled languages are how you stop asking it to guess — and the same model that would have guessed is the one that writes the notation for you. Humans supply intent, AI writes the DSL, humans read and agree. The hard part of stage 2 was always the typing, and the typing is the part we just automated.
