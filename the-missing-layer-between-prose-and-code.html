The Missing Layer Between Prose and Code: What STE and SQL Teach Us About Specs

5,200 words~23 min read2026-08-07

The premise

Specs as source has a load-bearing assumption: that if we write requirements carefully enough, an LLM can turn them into correct code. The problem is not effort. It is that free-form natural language — even organized with EARS — cannot carry the precision production software needs. Two engineers using different LLMs or different agents read the same paragraph and build two different systems. Neither is wrong, because the paragraph never decided.

The way out is a four-stage pipeline. The first three stages take ambiguity out of the spec, each one narrowing what the stage before left open. The last stage does a different job: it keeps the implementation from drifting away from the spec once the spec is settled.

Free-form natural language → Controlled language → Behaviour checks → Verified implementation

StageWhat it isWhat it removesWho checks it
1Free-form proseNothing — the baselineNobody can; it never decided
2Controlled languageInterpretation ambiguity, unstated constraintsA human reads it; a validator rejects the malformed
3aBehaviour checks: executable testing examplesAmbiguity about intended behaviour on the cases you thought of — the example is the answerA human skims the verdicts; the machine runs them
3bBehaviour checks: formal methodsAmbiguity on the cases nobody thought of — a property proved for every input, or a counterexampleA solver; a human reads only the property and any counterexample
4Verified implementationDrift between spec and codeThe machine, against stages 2 and 3

Most teams jump from 1 straight to unverified implementation (vibe it, hope), or from 1 to 3 (write tests, let the AI code). Stage 2 is the one everybody skips, and it is the only stage that fixes the spec itself rather than catching a bad spec's consequences downstream.

The last column is the point. Once stage 2 exists, people review through the notation: they read the DSL and the examples and properties written in it, never the implementation. Everything downstream is checked against it by machines, so human attention sits at the cheapest point in the pipeline. Stage 3 has two methods, testing examples and formal methods; the SQL section below works through both.

This post is about stage 2 and how to verify it, through two examples that are unusually instructive because they come from completely different worlds — aerospace maintenance manuals and relational data query languages — yet make the same move. One is a controlled natural language that never leaves English; the other is a formal query language the whole industry already accepted without ever calling it a spec tool. Between them they cover the full claim.

Two problems, one fix: the DSL

Strip spec-driven development down and there are exactly two things that can go wrong between a human's intent and a running system. They are usually lumped together as "the AI got it wrong," but they are different failures, sitting at different points in the flow — and the useful observation is that a single move closes both of them: introducing a DSL as the intermediate.

ProblemWhere it livesHow the DSL closes it
1 · Ambiguity of natural language — prose cannot carry the precision a requirement or design actually needs, so two readers build two systemsIn the spec, before any code existsThe DSL's closed vocabulary and single parse make imprecision impossible to write down (though not mistakes; see stage 3)
2 · LLM uncertainty — the same input, handed to a model, translates into different code on different runsIn the realization, spec → behaviourThe DSL is a machine-processable artifact, so a deterministic engine — a compiler, an interpreter, or a fixed engine reading it as config — turns it into behaviour the same way every time

It is one fix, not two, because the cure for the second failure is a consequence of curing the first. The DSL cures the ambiguity by construction: its precision is exactly the ambiguity of prose, removed. You cannot type a SQL query for "active customers with high spending" without deciding what active means, what high means, and over what window — the notation has slots, and empty slots are syntax errors or visible omissions. The imprecision is closed at the source.

And because the artifact is now a DSL rather than prose, the model's non-determinism is closed for free — as long as you resist re-introducing a model at the wrong step. The trap: if you ask an LLM to interpret the DSL afresh on every run, you have merely moved the non-determinism one step downstream, and the same input can still produce different behaviour. The escape is that a DSL, unlike prose, is machine-processable, so a deterministic engine can carry it to behaviour — and "engine" is deliberately broad. The DSL might be compiled to a general-purpose language and then built; interpreted on the fly by a fixed evaluator (SQL is exactly this — a query planner and execution engine read the statement the same way every time); or not turned into code at all, existing only as configuration that a generic engine reads, where the config carries the variable parts and the engine already holds the domain invariants. What matters is not which of these you pick but that the step is deterministic: the same DSL yields the same behaviour every time. Non-determinism is then confined to a single step (intent → DSL), which a human reviews once; everything after the reviewed artifact is a pure function, repeatable and auditable.

Config, in other words, is not the opposite of a DSL — it is one of the forms a DSL can take. A YAML file is a DSL when it has a closed vocabulary, a schema that rejects the malformed, and a fixed engine that gives it meaning. The rule file of an AI code reviewer is a vivid case, and an instructive one. Its structure is a DSL with general-purpose-language semantics: rules are imported from shared files (composition), an organization-wide best-practices file applies to every repository (inheritance), each rule is scoped private or public, and file patterns and blocking flags are applied by a fixed engine. But each rule's body is prose that an LLM interprets on every code review, which is exactly the step this post warns about. The structure is precise and verifiable; the rule text is not, which is why such rules have to be measured, with a simulator over past reviews and per-rule usefulness metrics.

So the two failures have one answer with two payoffs: the notation supplies the precision prose lacks, and being a machine-processable notation at all is what lets a deterministic engine — compiler, interpreter, or config runtime, not another LLM guess — carry it to behaviour. The rest of this post is the long form of that argument: two controlled languages that already work, how to verify them, and why that verification is what lets a DSL spec become the source of truth.

Simplified Technical English — a controlled natural language

ASD-STE100 Simplified Technical English is what you get when an industry constrains prose itself. Born in aerospace (originally AECMA Simplified English, 1986) for maintenance manuals read by non-native-English technicians under time pressure, STE is not a programming language — it is English with the ambiguity legislated out:

  • A closed dictionary of roughly 900 approved words, each with one approved meaning and one part of speech. follow means "come after" — if you mean "obey", the approved word is obey.
  • Roughly 60 writing rules: active voice, one instruction per sentence, sentence-length caps (about 20 words for procedures, 25 for description), no ambiguous participles, no omitted articles.
  • Technical names and verbs outside the core dictionary are allowed but must be declared for the project.

The effect, illustrated:

Unconstrained: "Ensure that the retaining bolt is not overtightened, as this may result in damage to the housing."

STE-style: "Do not tighten the retaining bolt to more than 12 Nm. More torque than 12 Nm damages the housing."

The rewrite is not shorter, it is decided. "Overtightened" had no referent; the rewrite forced a number to exist. That is the whole game at stage 2: a controlled language's real output is not cleaner text but a list of decisions someone had to make before they could write the sentence at all. STE is the proof of existence — you do not need to leave natural language to leave ambiguity, only to adopt a closed vocabulary and a single parse.

SQL — the DSL everyone already accepted

SQL is the most widely deployed stage-2 language in the industry, and nobody thinks of it as one.

Take a business request: "show me active customers with high spending." Three questions hide in seven words — what is active, what is high, over what window? Prose lets you ship that sentence into a backlog. SQL does not:

SELECT customer_id, SUM(order_total) AS spend_12mo
FROM   orders
WHERE  order_date >= CURRENT_DATE - INTERVAL '365 days'
GROUP  BY customer_id
HAVING SUM(order_total) > 1000
   AND MAX(last_login_at) >= CURRENT_DATE - INTERVAL '30 days';

You cannot type this without answering all three questions: SELECT / FROM / WHERE / GROUP BY / HAVING is a set of slots, and empty slots are syntax errors or visible omissions. Prose has no slots — that is exactly its problem.

SQL also shows the property that makes stage 2 economically viable: it is readable by the person who asked the question. An analyst who cannot write Java can read the query and say "no, 30 days should be 90." That review loop is the value — and hand-written test code mostly loses it, since a JUnit assertion is not something a business stakeholder audits. Stage 3a keeps the loop only when its examples stay at the level of the notation: rows in, verdict out.

What versus how: verify small, run big

SQL's deepest trick is not the slots. It is that the abstraction splits two kinds of difficulty that prose and hand-written code mix together:

The query owns whatThe engine owns how
Kind of difficultyBusiness ambiguity: what is active, what is high, over what windowExecution complexity: partitioning, shuffles, join order, indexes, spill to disk, retries, node failures
Who decides itThe requester, by reading the queryThe engine's planner and runtime, decided once by the engine's builders
Changes when you scale?No. The meaning of the query is the same on 4 rows and on 4 billionYes, completely, and invisibly to the query
How it is verifiedRun the query on a few hand-made rowsThe engine vendor's own test suite, amortized over every customer

That split is what makes SQL verifiable. Because the meaning does not depend on scale, you can check it on a laptop. Load four rows into DuckDB, SQLite, or a Postgres container, one per decision the query makes, and run the same query:

-- Stage 3 on a laptop: one row per decision, with the expected verdict
CREATE TABLE orders AS SELECT * FROM (VALUES
  ('alice', 1200, CURRENT_DATE - 10,  CURRENT_DATE - 2),   -- expect IN
  ('bob',   1000, CURRENT_DATE - 10,  CURRENT_DATE - 2),   -- expect OUT: not > 1000
  ('carol', 5000, CURRENT_DATE - 400, CURRENT_DATE - 2),   -- expect OUT: order too old
  ('dave',  3000, CURRENT_DATE - 10,  CURRENT_DATE - 90)   -- expect OUT: inactive
) AS t(customer_id, order_total, order_date, last_login_at);
-- run the query above: the result must be exactly {alice}

The requester reads four rows and four verdicts, not a distributed job. Then the same text goes, largely unchanged, to Redshift, Athena, Trino, Spark SQL, or BigQuery and runs over petabytes across hundreds of nodes. Nobody re-verifies the business logic at scale, because scale is not where the business logic lives. Nobody re-verifies the distributed execution either, because the engine is a fixed, deterministic program that the vendor already tests far harder than any single team could.

Mapped onto the pipeline: the query is stage 2, the four rows are stage 3a, and stage 4 mostly disappears for the user: the query is the implementation, and the engine that runs it was verified once, by its vendor, for everyone. This is the shape to copy in any DSL: keep the notation free of execution concerns, so its meaning can be checked small and then run big.

There is one honest leak. SQL dialects differ at the edges: date arithmetic, NULL ordering, integer division, string collation. If the laptop engine and the production engine disagree, the four rows have verified a different program. Keep the query in a portable subset, or transpile it with a tool such as sqlglot, and run the same examples against the target engine in CI.

Formal methods for SQL: checking every input, not four

Four rows check the cases you thought of. Formal methods check the ones you did not, and SQL is unusually well suited to them: its semantics are relational algebra, which has been formalized for decades, including the awkward parts such as NULL and bag semantics (Guagliardo & Libkin, 2017). One tool is enough to show the idea. SQLSolver (SIGMOD 2024) takes two queries and tries to prove they return the same result on every possible database. Point it at the AI's query and the reviewed one, or at a rewrite and the original.

Take a one-word slip a model could easily make: the recency test moves from HAVING to WHERE. Both queries parse, both run, and a reviewer skimming six lines can miss it.

SELECT customer_id, SUM(order_total) AS spend_12mo
FROM   orders
WHERE  order_date >= CURRENT_DATE - INTERVAL '365 days'
   AND last_login_at >= CURRENT_DATE - INTERVAL '30 days'   -- wrong clause
GROUP  BY customer_id
HAVING SUM(order_total) > 1000;

SQLSolver will not prove this query equivalent to the original, and one customer with two orders shows why:

-- counterexample: erin spent $2,010 this year and logged in 3 days ago
('erin', 2000, CURRENT_DATE - 100, CURRENT_DATE - 60),
('erin',   10, CURRENT_DATE - 5,   CURRENT_DATE - 3)
-- HAVING version: IN  (sum 2,010; latest login 3 days ago)
-- WHERE  version: OUT (only the $10 order is summed)

Formal reasoning says more than any set of examples can: as long as order totals are never negative, the WHERE version's result is always a subset of the HAVING version's. The bug can only drop customers, never add them. (Allow refunds as negative totals and the guarantee disappears, which is exactly the kind of assumption a solver forces you to state.) That is a statement about every possible table, and the requester only has to read one row of counterexample to understand it.

Two honest limits. Equivalence of arbitrary SQL is undecidable, so SQLSolver, like every tool of its kind, covers a fragment of SQL rather than all of it, and some query pairs come back unproven rather than proven or refuted. And a proof is only as good as the property or the reference query it is checked against, which someone still has to state and read. Formal methods do not replace the stage-2 review; they extend it from four inputs to all of them. Use 3a everywhere, and add 3b where a wrong answer is expensive.

"But DSLs are hard for humans to write"

This is the standard objection, and it was correct for thirty years. It is now the wrong frame.

The objection assumes the same person must both author and read the notation. Drop that assumption and a DSL's cost structure splits in two, along a seam that has always been there:

Hard for humans?Hard for AI?
Writing the DSLYes — you must learn the grammar, the operator set, the corner casesNo — closed vocabulary, small grammar, deterministic semantics, and a validator that says wrong out loud
Reading the DSLNo — that is what it was designed forn/a
Translating intent → DSLThe expensive partThis is the machine's best trick

So the workflow inverts. The human supplies intent in whatever form intent naturally arrives — "show me active customers with high spending" — and the model emits the notation:

SELECT customer_id, SUM(order_total) AS spend_12mo
FROM   orders
WHERE  order_date >= CURRENT_DATE - INTERVAL '365 days'
GROUP  BY customer_id
HAVING SUM(order_total) > 1000
   AND MAX(last_login_at) >= CURRENT_DATE - INTERVAL '30 days';

Then the human does the thing humans are good at: reads six lines and checks them. "Spend over $1,000 in the last year, logged in within 30 days — yes, that's what I meant by active and high." Total time: seconds. Checking the decisions (the numbers, the windows) needs no SQL expertise. Catching a clause-level slip does, which is what stage 3 is for.

Notice what happened in that loop. The ambiguity in the original sentence did not vanish silently — it got resolved into something visible. The model had to pick a number for "high" and a window for "active"; there is no way to stay vague. Every decision the prose left open now appears on the page where a reviewer can accept or reject it — "no, 30 days should be 90." That is the whole value of stage 2, and it survives the human never having learned to write the language.

Three reasons a DSL is specifically a good compilation target for an LLM, more so than general-purpose code:

  • Small, closed grammar. SQL's core query grammar is a handful of clauses; STE's dictionary is roughly 900 words with one meaning each. Fewer ways to be wrong.
  • A validator in the loop. Parser and type-checker reject malformed output immediately — a hard, cheap, non-negotiable signal, unlike a natural-language spec where nothing ever fails to parse. Every SQL engine ships a parser and planner; a controlled language like STE ships a checker that flags any word outside the approved dictionary.
  • Short output. Non-determinism compounds with length. A six-line query has far less room to drift than the few hundred lines of hand-rolled filtering, joining, and aggregation code you would otherwise have asked for — and that is the alternative. The choice was never "write SQL by hand or write English." It was "review six lines of SQL or review a few hundred lines of hand-rolled reporting job."

One limit on "easy for AI": it holds for notations the model has seen, like SQL. A private in-house DSL has no public corpus, and the model writes it confidently wrong. That is the strongest reason for the two forms in the next section, which ride on languages and formats models already know.

The asymmetry is the design goal, not a happy accident. A good stage-2 language is easy to read, easy to validate, and therefore easy to generate. Optimize a notation for human authoring ergonomics and you tend to add flexibility, shorthand, and multiple ways to say the same thing — which is exactly the ambiguity you were trying to remove. Optimizing for reading and checking pushes the other way. The DSL is not the artifact you write; it is the artifact you agree on.

One caveat follows directly: this loop only works if the human actually reads the output. Dense notation moves the failure mode from misunderstood to silently wrong, so AI-generated notation that nobody reviews is worse than prose — it looks authoritative and has nothing to trip an error against. The review step is not optional overhead; it is where the specification actually gets decided. And it is worth pairing with stage 3a: have the model emit worked examples — a few sample rows and the expected result — alongside the query, so you review behaviour and not just syntax.

You do not have to build a language

What kept DSLs rare was never the idea. It was the bill: a parser, a type checker, editor support, docs, and an onboarding tax on every team that has to adopt yet another syntax. Most teams can skip that bill entirely, because a DSL does not need its own syntax. Two forms reuse what teams already have:

A library in a general-purpose languageConfig with a schema
ExamplesAWS CDK in TypeScript, Python, Java, or Go; also LINQ, SQLAlchemy CoreCloudFormation YAML; also Smithy models, OpenAPI, and the structure of AI code-review rule files
What comes freeThe host language's IDE, type checker, tests, and package manager. Models already write the host language fluently.No new syntax to learn. Schema validation, and a fixed engine or code generator that gives the config its meaning.
What makes it verifiableThe library builds a model and emits a declarative artifact: cdk synth produces CloudFormation, which is diffed, linted, and reviewedThe validator rejects the malformed (smithy build, a JSON Schema), and the engine or generator is deterministic
Best fitEngineers author it, but the result must be reviewed and checkedThe spec crosses team or service boundaries, or non-engineers need to read it

Infrastructure is the clearest case, because both forms exist for the same domain and one compiles to the other. Here is the same encrypted, private S3 bucket as CloudFormation config:

Resources:
  LogsBucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketEncryption:
        ServerSideEncryptionConfiguration:
          - ServerSideEncryptionByDefault:
              SSEAlgorithm: aws:kms
      PublicAccessBlockConfiguration:
        BlockPublicAcls: true
        BlockPublicPolicy: true
        IgnorePublicAcls: true
        RestrictPublicBuckets: true

and as a CDK library call in TypeScript, which cdk synth turns into that YAML:

new s3.Bucket(this, 'LogsBucket', {
  encryption: s3.BucketEncryption.KMS_MANAGED,
  blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
});

The YAML is the contract either way: cfn-lint and cfn-guard check it, cdk diff shows changes to it, and the deploy engine executes it deterministically. What differs is who finds it approachable. A team that wants no new tooling writes the YAML directly and already has a verifiable spec. A team of engineers writes TypeScript or Java and gets types, autocomplete, unit tests, and reuse (one function for "every bucket we create is encrypted and private") for free. The library is the authoring surface; the config is the source of truth.

The library form has one condition, and it decides whether you still have a spec. The library must build something inspectable, not just run host code. CDK works because the construct tree becomes a template, and the template is the contract: a security reviewer reads cdk diff and policy tools such as cfn-guard check the synthesized output, never the TypeScript. A library that executes arbitrary host code directly (a lambda inside a filter, a callback at runtime) leaves an opaque hole where the analysis stops. The config form has the mirror-image risk: config that slowly grows loops and conditionals until it is a programming language with no debugger. CloudFormation itself shows the pressure, with Conditions, Fn::If, and later Fn::ForEach, and it is a large part of why CDK exists: move the loops into a real language, and keep the YAML declarative.

Either way, the contract is the same thing: the declarative artifact, written by hand as config or synthesized by a library. It is what validators, examples, and solvers check. With a library, engineers read the library code and reviewers read the synthesized diff, and because synthesis is deterministic the two cannot drift apart.

Embedded specs: making the spec the source

Birgitta Böckeler's survey of spec-driven tools names three levels: spec-first (written before the task, then left behind), spec-anchored (kept up to date as the feature changes), and spec-as-source (the only thing a person edits). Most tools stop at the first, because a prose spec drifts: nothing links it to the code, so the first change made without it makes it wrong. The attempts that get further give the spec a structure the toolchain reads. Three are in use today.

Interface first, with Smithy. You write the API model before any code, and the build generates clients, server stubs, and types from it:

/// Places an order. Fails with OutOfStock if an item cannot be reserved.
operation PlaceOrder {
    input := {
        @required
        @length(min: 1, max: 50)
        items: LineItems
    }
    errors: [OutOfStock]
}

In a typed language, code that disagrees with the model does not compile. Servers enforce the constraint traits on each request, Smithy Diff flags backward-incompatible changes, and the /// comments flow into the generated SDK docs and OpenAPI. The limit: Smithy fixes the boundary, not the behavior. "Fails with OutOfStock" is still prose.

Comments as specs, with Strands AI Functions. The function body is only a docstring. The docstring states the task, the return type (here a Pydantic model) states the shape, and an agent evaluates the function when it is called. Post-conditions check every result, and a failure goes back to the agent for another try:

def not_more_than_paid(r: Refund):
    assert r.amount_cents <= order_total_cents(r.order_id), "refund exceeds amount paid"

@ai_function(post_conditions=[not_more_than_paid], max_attempts=3)
def propose_refund(ticket: str) -> Refund:
    """Propose a refund for this support ticket under our policy:
    damaged items are refunded in full, late deliveries get 10% back.
    {ticket}"""

The comment cannot drift from the behavior, because the comment is what runs. The new risk is run-to-run variation. This is the model interpreting the spec on every call, the trap described in two problems, one fix, and the post-conditions are what keep it in check. The library's experimental verified mode removes the risk: the agent writes an implementation once and proves that it meets a contract for every input, Lean checks the proof, and the function then runs as compiled code with no model involved.

Annotations and contracts. The oldest approach attaches the spec to the signature:

/** Refunds part or all of an order. The amount may not exceed what was paid. */
public Refund refund(@NotNull String orderId, @Positive @Max(1_000_000) long amountCents)

A Bean Validation validator enforces the annotations on each call, and Javadoc and springdoc render them into the docs. The Javadoc sentence is still prose, because a single-field constraint cannot relate the amount to what was paid. Contract annotations can. JML's requires and ensures, SPARK's Pre and Post, Kani and Prusti in Rust, and Python's icontract state relations between inputs and results, and a checker or prover enforces them.

ApproachPrevents spec driftDocs on demand (like Javadoc)Precision control
Prose spec (baseline)No. Nothing links it to the code.Hand-written, and stale by default.None built in.
Interface first (Smithy)Strong at the boundary: generated code must match the model, and Smithy Diff flags breaking changes. Behavior can still drift.Strong: doc comments flow into SDK docs and OpenAPI.High for data (types, lengths, ranges, patterns, errors, custom traits). None for behavior.
Comments as specs (AI Functions)By construction, since the docstring is what runs. Run-to-run variation remains, bounded by post-conditions.Always current, and reused as the tool description other agents see. It reads like a prompt.A dial: prose, then a typed result, then post-conditions, then a contract with a proof.
Annotations and contractsStrong where a tool checks them. Descriptive annotations drift like comments.Strong: Javadoc, springdoc, sphinx-icontract.A dial: a description, then field constraints, then pre- and post-conditions, then a proof.

All three gave us more confidence than natural-language specs, for the same reason: part of each spec is read by a machine. A type, a constraint, a post-condition, or a contract cannot be read two ways, and it fails loudly when the code disagrees. Prose shrinks to what is hard to formalize, next to checks that catch what it misses.

Together they point to a direction we can call embedded specs. The spec lives inside an artifact the toolchain already processes (a model the build compiles, a docstring the runtime executes, an annotation a validator enforces), and the docs are generated from it on demand, the way Javadoc is. The condition on the library form above applies here too: the embedding must give a machine something to check. A docstring that only a model reads is still prose; add a typed result and post-conditions, and it is a spec. The three also combine: a model at the service boundary, contracts for the invariants inside a module, and comments as specs for the steps that need judgment. Wherever you use them, put the costliest rule, such as never refunding more than was paid, in the checked part.

In summary: build the abstractions, share the vocabulary

Prose cannot be the source of truth, because nothing can check it. A DSL can. People read it, a validator rejects the malformed, worked examples and formal methods check its behaviour, and a deterministic engine runs it. STE shows that precision does not require leaving English; SQL shows the whole loop, from reviewable notation to local checks to a deterministic engine; CloudFormation, CDK, and Smithy show that none of it requires inventing a language, and embedded specs carry the same checks into ordinary code.

So the call to action is not "adopt formal methods" or "write better prose". It is:

  • Build more domain-specific abstractions. A construct library, a Smithy model, a schema'd config: anything that turns a recurring decision in your domain into a slot that must be filled. Every abstraction like this is a place where an LLM stops guessing.
  • Align them on a common vocabulary. Agree once, for the domain, what an order, a customer, or an active account is. SQL works because every query over a database shares one schema; CDK works because every construct speaks CloudFormation's resource types. Two teams with precise private vocabularies still ship an integration bug at the boundary between them.
  • Extend standards before inventing. Where a vocabulary already exists (OpenAPI, Cedar, ISO 20022, SPDX), build on it; where none exists, defining it is the most valuable spec work your domain has left.

The payoff is that the line between spec and code disappears. With the right abstractions, code written on top of the DSL reads like the specification. The four CDK lines above say "an encrypted, private bucket" (and synthesize to a template that machines check says exactly that), and a SQL query says "customers who spent over $1,000 in the last year and logged in within 30 days". Yet they keep what prose never had: they are concise enough to review in seconds, precise enough that every decision is on the page, and verifiable by validators, examples, and solvers. Reading the code becomes reading the spec.

Humans supply intent, the AI writes the DSL, humans read and agree, and the DSL, not the prose, is the source of truth.
